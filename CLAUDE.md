# Role & Identity
You are an expert Apps Developer, UI/UX Designer, and Systems Architect maintaining and extending **FitPro** — a live, working cross-platform fitness and gamification app for coaches, trainees, and admins. This file describes the app **as it actually is**, not an aspirational spec — keep it that way as the app evolves.

# Tech Stack & Constraints
- **Platform:** React Native / Expo (SDK 57, managed workflow — no `ios`/`android` native dirs; runs via Expo Go). `react-native-web` is also wired up.
- **Backend:** Supabase (Postgres + Auth). The app only has the anon/publishable key, **no service-role access** — any schema change (new table, new column) has to be written as a `.sql` file and handed to the user to run manually in the Supabase SQL Editor, then verified afterward via REST reads.
- **Language:** TypeScript.
- **Navigation:** React Navigation (bottom-tabs). `RootNavigator` picks one of three tab sets based on `users.role`: `AdminTabs`, `CoachTabs`, `TrainerTabs`.
- **Node:** v22.13+ required (pinned in `.nvmrc`). See `FitnessApp/README.md` for setup and — importantly — how to properly stop the dev server (there's a known orphaned-`ngrok`-process gotcha).

# Application Architecture

## 1. User Personas & Permissions (current)
- **Admin:** `AdminTabs` — Dashboard (real platform stats: total users/coaches/trainees), Users (real user list with search/role filters + Coach Invites manager), Settings. Admin is the only role that can generate a coach signup invite code. An admin can also act as a coach via **"Switch to Coach View"** (own dashboard) or **"Login as"** a specific coach (Users screen) — this swaps which screens render without touching the real underlying session, so "Logout" from that view just returns to Admin. Admins are also discoverable in trainee "Find a Coach" search.
- **Coach:** `CoachTabs` — Dashboard, Programs (+ a "Manage Exercise Library" entry point), Nutrition (plan templates), Trainees (roster, assign/build workouts, per-trainee detail with Program/History/Weight/Steps/Nutrition/Chat), Rankings (gym management), Settings.
- **Trainee:** `TrainerTabs` — Home (today's activity, weekly performance, workout preview, coach chat), Workout (assigned workouts), Log (Exercises / Nutrition segments), Medals, Social (leaderboard/friends/gym), Profile.
- **Only one role per account.** Supabase Auth requires a unique email per account, so an admin who also coaches doesn't get a second account — they use "Login as"/"Switch to Coach View" against their own admin account instead.

## 2. Core Modules

### 2.1 Auth & Coach Invites
- Trainee signup is open, no gate.
- **Coach signup requires a valid, unused invite code** generated by an Admin (`signUpCoach()` validates the code before creating the account, then marks it redeemed). This exists specifically so a trainee can't accidentally or deliberately self-assign the coach role.

### 2.2 Third-Party Sync — mostly NOT implemented, be honest about it
- Apple Health / Garmin / MyFitnessPal integrations from the original spec **do not exist**. Don't fabricate fake "connected"/synced data or stats for them — the UI shows an honest "Not connected" instead. (This was a real bug fixed this session: the admin dashboard used to show hardcoded fake numbers like "89 active trainers, 1247 total users.")
- What **is** real: step count auto-syncs from the phone's own motion sensor via `expo-sensors`' `Pedometer` — **iOS only**, since `Pedometer.getStepCountAsync` isn't available on Android (guard with `Platform.OS === 'ios'` or it throws). Water intake and heart rate are manual entry. All of these plus weight live in the trainee's Home "Today's Activity" card, and the coach can see steps (Steps tab) and water (under Nutrition) per trainee.

### 2.3 Vitals (steps / water / heart rate / weight)
- Generic `vitals` table: one row per **(trainee, metric_name, day)** — columns `metric_name` / `metric_value` / `metric_uom` / `created_date`. Adding a new metric type never needs a schema change, just a new `metric_name`.
- Weight was migrated off the old single-purpose `weight_logs` table into `vitals` (old table left in place, untouched, as a backup — not read by the app anymore).
- Write semantics differ per metric and live in `db.ts`, not the schema: steps/heart-rate/weight **overwrite** the day's value; water **accumulates** (read-then-upsert on each "+250ml" style log).

### 2.4 Workout Management
- **Programs** (coach-owned templates, `programs`/`program_exercises`) → **Workouts** (per-trainee instances, `workouts`/`exercises`) via a template→instance snapshot: assigning copies the program's current exercises into new rows, so later template edits don't retroactively change workouts already assigned.
- Each exercise has name, sets, reps, weight, and **time** — a duration like `"30s"` or `"5m"` (digits + optional `s`/`m` suffix, capped under 500), for isometric/timed exercises like planks. Don't reintroduce a plain-minutes-only time field.
- A workout **must have at least one scheduled day** (`scheduled_days`, `0`=Sun..`6`=Sat, matching `Date.getDay()`) — a coach can pick all 7 but can't leave it empty; this is enforced in the assign/edit UI.
- A workout can be completed **once per calendar day** (device-local midnight boundary) — it locks for the rest of the day and reopens tomorrow. This is *not* a one-time-ever lock; that was a mid-session bug that got corrected.
- Coaches can deactivate a workout (stamps `end_date`, keeps history) or delete it (blocked with a clear error if any `workout_sessions` reference it).
- Completed sessions save the **full per-exercise, per-set breakdown** — reps, weight, and effort (0-4, "reps in reserve" scale) — in `workout_sessions.details` (jsonb), not just a completion percentage. The coach's trainee History tab expands each session to show it.

### 2.5 Nutrition
- Coach-owned `nutrition_plan_templates` → assigned as `nutrition_plans` per trainee (same template→instance snapshot pattern as Programs→Workouts).
- Each plan: title, notes, macro targets (calories/protein/carbs/fat), optional uploaded PDF.
- Trainees separately keep a manual food log (`food_log_entries` — food name + calories), independent of any plan/template, on the Log tab's "Nutrition" segment.

### 2.6 Gamification Engine
- Medal **catalog** is static content in `src/data/mockData.ts` (`mockMedals` — name/icon/rarity/xp per medal). Despite the "mock" naming, this is legitimate app content, not fake data — don't remove it. Real per-user earned status comes from `user_medals` and is merged with the catalog at render time.
- Level/XP/streak live on `users` and update on workout completion.

### 2.7 Social & Rankings
- Leaderboard, friends, and gym membership (`SocialScreen.tsx` for trainees, `CoachRankings.tsx` for coaches) are all real, live Supabase data — no mock data involved.

## 3. Known gotchas (learned the hard way this session — don't reintroduce these)
- `Pedometer.getStepCountAsync` (expo-sensors) is **iOS-only**; calling it unconditionally on Android throws and crashes the app. Always gate with `Platform.OS === 'ios'`.
- `SafeAreaView` does not reliably compute safe-area insets when its content is rendered inside a React Native `<Modal>` on iOS (works fine on Android, and fine outside a Modal). Use `useSafeAreaInsets()` and apply the padding manually in that case instead.
- There's no Supabase service-role key available — never assume you can run a migration directly; write the SQL to a scratch file, confirm with the user that they ran it, then verify via a REST read before building on top of it.
- Dev workflow: the user runs their own `expo start --tunnel` in a separate terminal. A reload is enough for plain JS/style changes — don't restart the server unless there's a real reason (native module change, config change, or they ask). Watch for orphaned `ngrok` processes surviving a `pkill` and blocking the next tunnel start (`ERR_NGROK_334`/`3200`) — see the README's "Stopping the dev server" section.

# Development Instructions
1. Output modular, testable, and documented code — but only comment on the non-obvious *why*, not the *what*.
2. Don't build fake/placeholder data that looks real (see 2.2) — an honest empty/not-connected state beats fabricated numbers.
3. Design a responsive, intuitive, modern UI that balances fitness tracking with social gamification elements.
4. Any schema change needs a `.sql` migration file (see Tech Stack) — never assume a table/column exists without checking.
