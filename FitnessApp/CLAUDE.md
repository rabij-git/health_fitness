### Android Emulator

**Step 1 — Start the emulator:**
```bash

```

**Step 2 — Launch the app (must be run in an interactive terminal / TTY):**

- **Use `--tunnel` mode** — `adb reverse` + direct LAN is unreliable on this machine. Tunnel (ngrok) bypasses local network issues.

- **Expo CLI requires an interactive terminal (TTY)** — run directly in a terminal tab, not via `!` in Claude Code.

**Troubleshooting — `npx expo start --tunnel` fails to start at all:**
ngrok's backend now requires an authenticated account + a modern (v3+) agent even for anonymous tunnels, which the version Expo bundles (`@expo/ngrok`, agent v2.3.41) can't satisfy, and Expo's own CLI forces a globally-shared authtoken + custom `exp.direct` hostname that collides across every Expo dev on the internet. Fixed durably via `node_modules` patches reapplied by `postinstall` (`scripts/patch-ngrok.js`, wired into `package.json`) — **do not hand-edit `node_modules` again, edit `scripts/patch-ngrok.js` instead** and the patches will reapply on the next `npm install`:
1. Swaps the bundled ngrok binary for a modern v3 one kept in `tools/ngrok-v3-darwin-arm64`.
2. Patches `@expo/ngrok/index.js`'s `connectRetry` to strip `authtoken`/`configPath`/`port` before calling `startTunnel()` (v3's strict schema rejects those extra fields) and to regenerate the tunnel's auto-name on each retry (a race where the agent's tunnel-creation API is hit before its cloud session finishes handshaking can leave a "ghost" name registered, which then fails a same-named retry with `error_code 102 "already exists"` — not covered by ngrok's own retriable-error list).
3. Patches `AsyncNgrok.js` (in `node_modules/expo/...`) to stop forcing Expo's shared authtoken/`exp.direct` hostname, so it falls back to the user's own already-authenticated `~/.ngrok2/ngrok.yml` account and a plain random `*.ngrok-free.dev` URL instead.
- The user's personal ngrok account must be authenticated once (`ngrok authtoken YOUR_TOKEN`, v2-syntax CLI even though the config format is v3) — already done for this machine.
- Verify success by checking for `Tunnel connected.` / `Tunnel ready.` in the CLI output (or query `curl http://127.0.0.1:4040/api/tunnels` for the live `public_url` while it's running).

**Troubleshooting — emulator stuck bundling / "Failed to download remote update":**
The emulator's virtual network can get corrupted after the Mac sleeps while it's running (symptoms: bundling hangs, or Expo Go throws `java.io.IOException: Failed to download remote update`; `adb shell ping 8.8.8.8` returns garbage/negative round-trip times when this happens). Fix is a cold restart, not a reload:
```bash
adb emu kill
# wait for the qemu-system process to fully exit, then:
/opt/homebrew/share/android-commandlinetools/emulator/emulator -avd Pixel_6_API_34 -no-audio -no-snapshot
```
Verify with `adb shell ping -c 3 -w 5 8.8.8.8` before assuming the app itself is broken.

This is the overwhelming majority of the original 152 call sites — if a *new* button or accent is added, default it to `colors.primary`, and only reach for `colors.danger` if it's a genuine delete/error/reject/over-limit case matching the list above.
  - **`progressFillWater`** (`FoodLogScreen.tsx`, the water-intake progress bar's fill) is neither — it's not an over-limit indicator (no second "over" segment, just clamped at 100%), just an arbitrary color pick that needed to stay visually distinct from the calorie bar's cyan `progressFill` right above it, so it was pointed at `colors.accent` instead of either `primary` or `danger`.
- **Font (Poppins)** — the mood board only showed a bold/geometric vibe, not a named typeface; the user was asked and chose to add a real font (over keeping the system default) despite the extra work. Loaded via `@expo-google-fonts/poppins` + `expo-font`'s `useFonts` in `App.tsx` (weights 400/500/600/700/800/900), gated behind a plain indigo `<View>` fallback while loading — this works directly in Expo Go, no native rebuild needed, since `expo-font` loads TTF assets at JS runtime.
  - **Global application without touching ~700 individual style objects:** every screen imports `Text`/`TextInput` from **`src/components/AppText.tsx`**, not `'react-native'` directly (see each screen's import line — `Text` alone, or `Text, TextInput` together, depending on what that file uses). That wrapper is the one and only place that knows about Poppins.
  - **Why a wrapper, and why per-fontWeight font files, not a single global fontFamily:** RN's `Text`/`TextInput` are function components in this RN version (0.86), not classes — the old `Text.render`/`Text.defaultProps` monkey-patch tricks for "inject a global font" don't work here (no static `.render`, function components don't support `defaultProps`). Separately, and more importantly: **iOS silently ignores `fontWeight` entirely once a custom `fontFamily` is set** (Android fakes/synthesizes bold on top of a custom font; iOS does not) — so a single Poppins family injected globally would make every one of this app's many `fontWeight: '700'/'800'/'900'` headers/buttons render as plain-weight text on iPhone specifically, while looking fine on Android. `AppText.tsx`'s `WEIGHT_TO_FONT` map sidesteps this by mapping every `fontWeight` value already used in the app (500/600/700/800/900, plus the implicit default 400) to the matching real Poppins face (`Poppins_600SemiBold`, `Poppins_800ExtraBold`, etc.) — reading whatever `fontWeight` is already in that Text's own `style` (via `StyleSheet.flatten`) and setting `fontFamily` accordingly, so every existing bold-weight style keeps rendering bold, identically, on both platforms.
  - **`TextInput` is `forwardRef`, not a plain function component, specifically so ref-based `.focus()` calls keep working** — several modals across the app (see "autoFocus inside a transparent animationType="slide" Modal" further down) focus a `TextInput` ref from a `Modal`'s `onShow` instead of using `autoFocus`. `AppText.tsx` also declares `export interface TextInput extends RNTextInput {}` alongside the `const TextInput = forwardRef(...)` — this dual value+type declaration (mirroring how RN's own class-based `TextInput` naturally serves as both) is what lets existing call sites keep writing `useRef<TextInput>(null)` unchanged.
  - **If a new screen is added, import `Text`/`TextInput` from `../../components/AppText` (or `../components/AppText` for a file directly under `src/screens/`), never from `'react-native'` directly** — that's the only thing that makes the font system apply to it.

## UI / UX Decisions Made

### Login Screen
- Role selection highlight color: the brand accent (`colors.xpBar`/`colors.primary` — both Neon Cyan `#22D3EE`), NOT red (`colors.danger`, reserved for delete/error — see "Branding" above)
- Selected state uses: `borderColor: colors.xpBar`, `backgroundColor: '#0a1f1a'`, icon/label also in `colors.xpBar`
- Sign-in password field has no placeholder dots — starts genuinely blank
- **Email confirmation is a Supabase Auth *project setting* (Dashboard → Authentication → Providers → Email → "Confirm email"), not app code — recommended OFF for this app.** With it on, `signUp()`/`signUpCoach()`/`signUpTraineeWithInvite()` return a null `session` until the trainee/coach clicks a confirmation link, and Supabase's own built-in email sender is unreliable for this without a custom SMTP provider configured (rate-limited, meant for testing only) — in practice this meant new signups got stuck on "check your email" with no email ever arriving. Nothing else in the app depends on outbound email working (there's no password-reset flow either), so there's no real cost to leaving it off. `handleSignUp` (`LoginScreen.tsx`) reacts to whichever way it's actually configured rather than assuming: if `signUp`'s response includes a real `session` (confirmation off), it fetches the profile and calls `onLogin(...)` immediately, logging the new account straight in — the "Account created! Check your email to confirm..." message only shows as a fallback if `session` comes back null (confirmation still on).

### Add (+) Button
- **AdminUsers:** small orange (`#FF8C00`) icon button, `marginRight: 12` to keep it tappable on Android — unchanged/unverified this session.
- **CoachPrograms:** now a full-width orange **"Add Program"** button pinned above the list (not gated behind the list's loading state — see Robustness Pitfalls below), so it's always reachable even if the program list is slow or fails to load.

### Header Avatar Button (Logout)
Both `TrainerDashboard.tsx` (trainee Home) and `CoachDashboard.tsx` show a `log-out-outline` icon in the top-right header button instead of the user's initials — the button still calls `onLogout` directly (no confirm step), but the icon makes the action self-evident instead of looking like a profile shortcut.

### Workout Screen (Trainee)
- **Per-set table layout** with columns: `SET | REPS | WEIGHT | EFFORT`
- Each exercise shows one row per set (not a single combined row)
- Coach reps shown as **single numbers** (e.g. `8`, not `8-10`)
- **Reps field:** display-only for the trainee, same as weight — trainees follow the coach-assigned rep count and can't edit it (previously an editable number-pad input clamped to `coachReps + 8`; changed so a trainee can't modify the prescribed reps for their own workout).
- **Weight field:** Display only for the trainee — no keyboard, no editing
- **Effort rating:** per-set buttons 0–4 (RIR — Reps In Reserve), colors `#4CAF50 → #8BC34A → #FF9800 → #FF5722 → #E94560`. **Deselectable** — tapping an already-selected rating clears it back to `null` instead of being stuck once picked.
- **Exercises must be done in order, and so must their sets.** `activeExerciseIndex` (`WorkoutScreen.tsx`) is the index of the first not-yet-`completed` exercise (or `exercises.length` once every exercise is done) — only that one exercise is interactive; everything before it (already completed) and after it (not reached yet) is locked: effort buttons disabled, and the per-exercise checkbox is either non-interactive (past — can't un-complete and jump back) or replaced with a lock icon (future — can't skip ahead), with a "Complete the previous exercise to unlock" hint and a dimmed card. **Within the active exercise, sets are gated the same way** — `activeSetIndex` is the first set with no logged effort (or `sets.length` once all are logged); only that one set's effort buttons are enabled, so a trainee can't jump to set 3 before logging set 1 and 2. **The checkbox auto-ticks and is no longer manually tappable.** A `useEffect` marks an exercise `completed` the instant every one of its sets has a logged effort, advancing the trainee to the next exercise automatically — the checkbox itself is a pure status indicator now (a plain `View`, not a `TouchableOpacity`), not an early-finish override. This was removed deliberately (per feedback): a trainee could previously tick an exercise done without logging any sets at all, skipping past it; now the only way to complete an exercise is to actually fill in effort for every set.
- **Rest timer between sets:** each exercise has an optional coach-set `rest_seconds` (both `exercises` and `program_exercises`, migration `/private/tmp/scratch/exercises_rest_seconds.sql`, already run) — surfaced as a "REST (SEC)" field, right next to "TIME (S/M)", clamped 0–600 via `sanitizeCount`. Set on **both** ends of the template→instance pattern: `CoachPrograms.tsx`'s Add/Edit Program exercise builders (program templates) and `CoachTrainees.tsx`'s assign/edit-workout exercise builders (per-trainee workouts) — a program's rest values carry over into a workout on assignment, same as sets/reps/weight/time. On the trainee side, logging an effort rating (not clearing one) for a set starts a countdown if that exercise has `restSeconds > 0` — a floating banner (`WorkoutScreen.tsx`) shows the exercise name and a live `M:SS` countdown, and **for the final 3 seconds only** ("3... 2... 1...", tightened from an earlier 5-second version per feedback that it didn't match the intended countdown) a short synthesized tick plays once per second (`assets/sounds/tick.wav`, played via `expo-audio`'s `useAudioPlayer`/`seekTo(0)`+`play()`) **and the phone vibrates** (`Vibration.vibrate(200)`, `react-native`'s built-in API, no extra dependency) so the trainee knows to start the next set without watching the screen — the vibration fires unconditionally (foreground or background, sound-on or silent-switch), specifically so a trainee with the phone on silent still feels it; the tick sound itself still respects the foreground-only/`try-catch` guard below. While the countdown is running, every effort button across the entire workout (not just the resting exercise) is disabled and dimmed — the trainee can't log another set or jump to a different exercise mid-rest. **No rest timer at all fires after the very last set of the very last exercise** — `isVeryLastSet` (`exIndex === exercises.length - 1 && setIndex === exercise.sets.length - 1`) skips starting a countdown there regardless of that exercise's `restSeconds`, since the workout is already finished at that point and a rest period makes no sense. This requires a full dev-server restart (not just a reload) the first time, since `expo-audio` is a newly-installed dependency.
- **Finish gating:** the Finish button is disabled (with a hint text) until at least one set has a logged effort rating — previously a workout could be "finished" with zero progress logged, which still counted toward medal eligibility and sent a misleading "0% done, +0 XP" notification to the coach.
- **History integration:** finishing a workout still writes an `exercise_weight_logs` entry (via `logExerciseWeight`) for every exercise that had at least one set's effort logged, using that day's coach-assigned sets/reps/weight — this write is kept for potential future reporting, but nothing currently reads it (see below). `ExerciseLogScreen.tsx` (the Workout tab's "History" segment — see Navigation) is **read-only**, sourced from `workout_sessions` (`getTraineeHistory(userId, 200)`), not `exercise_weight_logs` — no manual entry ever existed here for the trainee to type into. It was originally a per-exercise weight-progression view (mini bar chart + history table of weight/sets/reps per exercise); per feedback that weight tracking wasn't useful here, it was replaced with two things: a "Days Exercised" bar chart with a Week/Month toggle (`buildWeekBuckets`/`buildMonthBuckets` — each bar counts **distinct calendar days** with a completed session in that week/Sunday-start or calendar month, not raw session count, so two workouts on the same day still count as one active day), and a "Completed Workouts" table listing every session's date, time, and workout name, newest first.
- **Medal XP is real:** earning a medal on finish now actually adds its `xpReward` to the trainee's XP total (on top of the workout's own XP), instead of just being a number the medal-toast displayed that nothing added up to.
- **Workout locking mid-session:** once at least one set has a logged effort and the workout hasn't been finished yet (`sessionActive = loggedSets > 0 && !submitted`, `WorkoutScreen.tsx`), the trainee can't switch to or start a different workout. The "‹ All Workouts" back row is replaced with a disabled "Workout in progress — finish to switch" indicator, and the Home screen's `openWorkoutId` deep-link effect (see "Workout Today" card below) is guarded to no-op — clearing the route param without changing `selectedWorkoutId` — if it would jump to a *different* workout while a session is active. Re-tapping the *same* in-progress workout is still fine. Unlocks automatically once `submitted` flips true on Finish.
- **All active-session state lives in `src/contexts/ActiveWorkoutContext.tsx`, not `WorkoutScreen.tsx`'s own component state.** Originally this was all local state in `WorkoutScreen.tsx`, backstopped by an `AsyncStorage` round-trip (`src/lib/workoutProgress.ts`, still described below) for the "closing the screen/app loses progress" bug. That backstop turned out not to be enough in practice — the report came back that switching to the Workout tab's "History" segment, or just backgrounding the app, *still* lost progress. The real fix is architectural, not another storage tweak: `WorkoutTabScreen.tsx` conditionally *renders* `WorkoutScreen`/`ExerciseLogScreen` rather than hiding one, which is a genuine unmount+remount of `WorkoutScreen` every time — so anything living only in `WorkoutScreen`'s own `useState` was never going to survive that reliably regardless of how careful the disk-persistence logic was. `ActiveWorkoutProvider` now wraps `TrainerTabs.tsx`'s entire `Tab.Navigator` (mounted once, for the whole trainee session, never torn down by a tab switch or the History toggle) and owns the workout list, the selected workout and its exercises/sets/effort, the rest timer, and the Finish/submit flow — `WorkoutScreen.tsx` is now a thin presentational consumer (`useActiveWorkout()`) that can mount and unmount freely without the actual session data ever being at risk. Because `TrainerTabs.tsx`'s own function body sits *above* its `Tab.Navigator` (only its `Tab.Screen` children are inside a `NavigationContext`), the Provider's own data-loading uses plain `useEffect`/`setInterval`/`AppState` listeners rather than `useFocusEffect` — there's no focus event available to hook at that level, and there doesn't need to be, since the Provider's load effect now only needs to run once per app session rather than on every focus.
  - **The on-device `AsyncStorage` backstop (`src/lib/workoutProgress.ts`) stays, unchanged, as the last line of defense for an actual app *kill*** — the Provider is still just in-memory React state, gone the instant the JS context itself is destroyed (not just a tab switch). Every `exercises`/`restTimer` change writes the current session (`workoutId`, device-local `dateStr`, `sets` per exercise id, the running rest countdown's real `endAt` epoch timestamp) to disk, scoped per trainee (only one in-progress session is ever allowed at a time). On the Provider's one-time mount, it loads this saved session and — only if it's from *today*, the workout is still active, and not already completed — auto-selects it and merges the saved per-set data back into `buildInitialExercises`'s fresh output. Cleared on a successful Finish; a failed save deliberately leaves it in place so a retry after a server error doesn't lose the trainee's work either.
  - **The rest timer is now visible on every tab, not just Workout** (`src/components/RestTimerBanner.tsx`, rendered once in `TrainerTabs.tsx` as an absolutely-positioned sibling above the `Tab.Navigator`, reading from the same `ActiveWorkoutContext`) — reported bug: the countdown kept running correctly in the background, but the banner showing it used to live inside `WorkoutScreen.tsx`'s own JSX, so it disappeared the moment the trainee switched to a different tab even though the rest period was still active. Tapping it jumps back to the Workout tab (via a `navigationRef` threaded down from `RootNavigator.tsx`'s `NavigationContainer`, since the banner itself isn't a `Tab.Screen` and can't call `useNavigation()` directly).
  - **Double-tap the banner to skip just that one rest period** — there's only ever one active rest timer at a time (`ActiveWorkoutContext`'s `restTimer` is a single value, not a list), so "skip" (`skipRestTimer()`, a plain `setRestTimer(null)`) inherently only ever cancels the current period; it needs no extra "which one" bookkeeping to keep it from accidentally skipping a *future* rest period too. Detected with a simple `lastTapRef`/`Date.now()` diff (<350ms counts as a double-tap) rather than a gesture library, since this is the only double-tap anywhere in the app.
  - **A running rest countdown is saved and restored too** (`SavedRestTimer`, `workoutProgress.ts`) — the saved snapshot's `endAt` is a real epoch timestamp, so the restore only reapplies it if it's still in the future (if the rest period already finished while the app was away, it's just over, same as if the trainee had been watching it the whole time — no special-casing needed). **Known minor gap, not fixed:** if the countdown's rest-end local notification (see below) was already scheduled before an app-kill-and-relaunch, restoring the timer schedules a second one for the same moment — a harmless duplicate ping, not incorrect timing, left alone rather than adding cross-relaunch notification-id bookkeeping for it.
- **Trainees can reorder upcoming exercises mid-workout** (`reorderExercise(exerciseId, direction)`, `ActiveWorkoutContext.tsx`) — small up/down chevrons next to each exercise's name in `WorkoutScreen.tsx`, visible on any exercise at or after `activeExerciseIndex`. Deliberately scoped to *this session's in-memory order only* — it swaps two entries in the `exercises` array (persisted alongside everything else in `workoutProgress.ts`, so it survives a kill/remount like the rest of the session), but never writes back to the coach's underlying `exercises`/`sort_order` row, since this is the trainee picking a different order for themselves today, not editing what the coach assigned. Already-`completed` exercises can't be moved (same in-order-completion lock that already governs which exercise/set is interactive) — letting a completed one move would silently misrepresent what was actually done in what order.
- **The "EFFORT SCALE" legend moved to the top of the screen** (right after the progress bar, before the exercise cards) — it used to render once, after every exercise card, which meant a trainee had to scroll past the entire workout to find out what the effort numbers even meant. Reported as wanting the legend visible with "the current exercise below it."
- **Single-arm / single-leg exercises show a badge** (`exercise.laterality`, `'single_arm' | 'single_leg' | null` — see "Exercise Input Rules" below for where a coach sets this) next to the exercise name, same visual treatment as the existing time badge.
- **Rest timer survives backgrounding:** the countdown used to be a plain decrement-every-second `setTimeout`, which just stops advancing while the app is backgrounded (RN fully suspends JS timers) — the display would sit frozen at whatever it showed when backgrounded, understating how much rest time had actually passed. Reworked to compute remaining time from a fixed `endAt` epoch timestamp (`Date.now() + restSeconds * 1000`) rather than decrementing a counter, recomputed every second via `setInterval` and additionally recomputed immediately on an `AppState` `'change'` → `'active'` event so it snaps to the correct value the instant the app comes back to the foreground instead of waiting up to a second for the next tick.
  - **The in-app tick sound is guarded against a real crash:** `tickPlayer.play()` (for the final-5-seconds tick) is only attempted when `AppState.currentState === 'active'`, and wrapped in `try/catch` regardless — iOS throws `UnexpectedException: Session activation failed` **synchronously** (uncaught, crashes the whole app) if audio session activation is attempted while backgrounded or mid-transition (repro: background the app during rest, foreground briefly, background again right before the timer's final 5 seconds). See Robustness Pitfalls #9 for the general lesson.
- **Rest-end local notification (`src/lib/restNotifications.ts`):** so the trainee is alerted even after leaving the app during rest (checking email, social media, etc.) — `expo-audio` alone can't play sound in the background, since that needs the iOS "audio" background mode + Android foreground-service audio, neither of which Expo Go can declare. Instead, `scheduleRestEndNotification(exerciseName, totalSeconds)` schedules a **local** notification (`expo-notifications`, `SchedulableTriggerInputTypes.TIME_INTERVAL`) for the moment the rest timer starts, and `cancelRestEndNotification(id)` cancels it in the effect's cleanup (new rest timer started, or the effect torn down) — wired into the same `useEffect` in `ActiveWorkoutContext.tsx` (moved here along with the rest of the rest-timer state — see above) that runs the countdown, keyed on `restTimer?.endAt`, notification id tracked in a `ref` (not state — pure bookkeeping, no re-render needed).
  - **Suppressing the double-alert:** `Notifications.setNotificationHandler` (registered once, at app start via a side-effect-only `import './src/lib/restNotifications'` in `App.tsx`) checks `AppState.currentState` — while foregrounded, the in-app banner/tick sound already covers it, so the system notification's banner/sound is suppressed (`shouldShowBanner`/`shouldShowList`/`shouldPlaySound` all `false`); while backgrounded, it shows and plays normally.
  - **Permission handling:** `ensurePermission()` requests once via `Notifications.requestPermissionsAsync()` if not already granted, and — if denied — doesn't re-prompt on every subsequent rest period that session (`permissionDeniedThisSession` flag); denial just means no background alert, not a broken feature (in-app sound/banner still work while foregrounded).
  - **The module is loaded lazily, not via a static top-level `import`** — a real crash (`[runtime not ready]: expo-notifications: Android Push notifications... removed from Expo Go...`) happens the instant `expo-notifications` is *imported* on Android inside Expo Go, regardless of only using local notifications here. `restNotifications.ts` uses `import type * as NotificationsType from 'expo-notifications'` (types only, erased at compile time) plus a `getNotifications()` helper that `require()`s the real module only when NOT `Platform.OS === 'android' && Constants.executionEnvironment === ExecutionEnvironment.StoreClient` (`expo-constants`, added as a direct dependency for this) — every exported function no-ops when it's unavailable rather than crashing. See Robustness Pitfalls #10 for the general lesson.
  - **Android custom sound lives on the notification *channel*, not the notification content** — `ensureAndroidChannel()` creates a `'rest-timer'` channel once with `sound: 'tick.wav'` (referencing the file by name, as bundled via the plugin config below); iOS instead sets `sound` directly on the notification content.
  - **Requires a native rebuild, not just a JS reload — and only fully works in a dev-client/EAS build, not Expo Go.** `app.json`'s `expo-notifications` plugin entry (`{ "sounds": ["./assets/sounds/tick.wav"] }`) bundles the tick sound into the native project so it can be referenced by filename — this is a native/config-plugin change, so `expo start` alone won't pick it up; needs `npx expo run:ios`/`run:android` (or an EAS dev-client build) to take effect. **The notification itself still fires in Expo Go** (permission prompt, banner, default system sound) — only the *custom* tick sound specifically needs the native build, since Expo Go can't register a custom notification sound reliably.

### Exercise Input Rules (coach-facing: program templates, workout assignment, exercise library)
Shared sanitizers in `src/lib/exerciseInput.ts`, used by `CoachPrograms.tsx`, `CoachTrainees.tsx`, and `ExerciseLibraryManager.tsx`:
- `sanitizeCount(v, min, max)` — digits only, clamps in range. Sets: 1–6. Reps: 1–30.
- `sanitizeWeightInput(v)` — digits + single decimal point, blocks a bare `"0"`. The field only takes the number; **`kg` is appended automatically** on save (`withKg`), stripped back off when re-editing (`stripKg`) — the coach never types "kg".
- Trainee's own body weight (`TrainerDashboard.tsx`) has separate rules: numeric only, max 200kg, rejects 0, Save button disabled while invalid.

### Assigned Workout Duration (Weeks) — `workouts.duration_weeks`
A per-trainee-instance-only field, deliberately separate from two other, differently-scoped "duration"-shaped fields already in the schema: `workouts.duration` (a per-session length string like `"60 min"`, hardcoded, not user-editable anywhere) and `programs.duration` (an always-required weeks value on the coach's reusable TEMPLATE — `sanitizeCount`'d 1–20, defaults to `'8'` if left blank at template creation). `duration_weeks` (migration: `scripts/workouts_duration_weeks.sql`, nullable int, DB-level check constraint 1–52) is how long **this specific assignment** is meant to run — **optional**, since a coach may not always want to commit to a program length up front, and it can legitimately differ per trainee even when assigned from the same template.
- **Assign flow (step 2 "Build Workout"):** `selectProgram` pre-fills `workoutDurationWeeks` from the selected program's own `duration` as a starting suggestion, but it's freely editable/clearable right there (`sanitizeCount(v, 1, 52)`, empty allowed) — a "DURATION (WEEKS, OPTIONAL)" field, saved via `createWorkout`'s `duration_weeks` param.
- **Edit Workout modal:** same field, pre-filled from the workout's *current* `duration_weeks` (not re-derived from the program) via `openEditModal`, saved via the new `updateWorkoutDurationWeeks(workoutId, weeks)` (`db.ts`), alongside the existing exercises/scheduled-days updates in `saveEdit`.
- **Display:** shown in the workout row's meta line (`CoachTrainees.tsx`'s Program tab list) as `"· N wks"` only when set — an honest omission, not a fake "—" placeholder, when a coach never filled it in. **Now also surfaced on the trainee side** (`WorkoutScreen.tsx`, per later feedback — "so that the coach and trainee knows how long the program is for"): `durationWeeksLabel()` appends `"N wks program"` to every workout-picker card's meta line (To Do/Completed Today/Not Today/Past) and to both the read-only and active-logging header's meta line, reading `selectedWorkoutMeta.duration_weeks` directly (that variable is already a `DBWorkout`, unlike `dbWorkout` which is the app-level `Workout` shape without this field) — omitted the same way when unset, no fake placeholder.
- **"Which block is being modified" clarity (coach side):** the Edit Workout modal's header previously showed only "EDITING PROGRAM" + the trainee's name — with a trainee able to have several assigned workouts (see "Multiple Workouts Per Trainee"), that gave no indication of *which* one was open. Header now reads "EDITING WORKOUT · {trainee name}" with the actual workout name as the modal's main title, plus a small calendar-icon `blockDurationBadge` chip under it showing "{N} weeks program" when `editDurationWeeks` is set — so both which workout and how long it runs for are visible without scrolling down to the read-only Workout Name field. The trainee already gets equivalent clarity from the workout-picker flow itself (they tap a specific named card, and the selected workout's own name stays in the header the whole time it's open).
- **`duration_weeks` is a real expiration, not just a label.** Per explicit feedback ("a coach cannot edit a program if it's more been more than the duration assigned to it, a trainee cannot do the program if it's over the duration, the duration is the end date of the program"): `src/lib/workoutDuration.ts` (`isWorkoutDurationExpired(workout)`, `getWorkoutEndDate(workout)`, `formatWorkoutEndDate(workout)`) computes an end date as `created_at` (when the workout was assigned) + `duration_weeks` weeks, compared as calendar dates (not raw timestamps, so the assignment day and the final day both count in full — same device-local-midnight-boundary convention as the existing "once per day" completion lock). No schema change — derived purely from two columns that already exist.
  - **Coach side:** `openEditModal` (`CoachTrainees.tsx`) refuses to open — an `Alert.alert('Program Ended', ...)` instead — for a workout past its own `duration_weeks`, directing the coach to deactivate it and assign a fresh one rather than implying an "extend" path that doesn't exist (editing, including changing `duration_weeks` itself, is exactly what's blocked). The workout list row shows a "Duration Ended" tag + "Duration ended {date}" in its meta line, and its Edit button is visually greyed (`workoutActionBtnDisabled`) — but still tappable rather than `disabled`, so tapping it surfaces the Alert's explanation instead of doing nothing (silently-dead buttons are a documented anti-pattern in this file — see Robustness Pitfalls). **The Active/Inactive `Switch` and delete button are deliberately untouched by this check** — a coach can still retire or delete an expired workout; only *editing its content* is blocked. This is independent of the manual `active`/`end_date` toggle: a workout can be `active: true` in the DB yet still read as expired-and-uneditable purely from having run past its assigned weeks.
  - **Trainee side (`WorkoutScreen.tsx`):** an expired-but-still-`active` workout no longer lands in "To Do" or "Not Today" — it gets its own **"PROGRAM ENDED"** picker section (flag icon, read-only, same tappable-card pattern as Past/Not Today), and selecting it adds a new `readOnlyReason: 'expired'` (checked ahead of `'completed'`/`'notToday'`, after `'inactive'`) with its own banner ("This program's assigned duration ended {date} — ask your coach for a new one.") — no logging, no Finish, same as every other read-only reason. Distinct from the "Past" section, which is for a coach's manual `active: false` toggle — a program can run out of weeks on its own without the coach ever touching the Active switch.
- **Once set, `duration_weeks` is a one-time, permanent commitment — per feedback ("once the duration is entered for a program it cannot be changed").** This is a *separate* rule from the expiration above: it locks the moment a value is first saved, not only once that value's time has elapsed. `updateWorkoutDurationWeeks(workoutId, weeks)` (`db.ts`) re-fetches the row first and throws if `duration_weeks` is already non-null — the one real enforcement point, since there's no service-role access to add a DB trigger. `CoachTrainees.tsx`'s Edit Workout modal mirrors this client-side via `editDurationWeeksLocked` (set in `openEditModal` from `workout.duration_weeks != null`): locked renders a read-only chip ("Locked — once a duration is set it can't be changed. Assign a new workout instead.") instead of the input, and `saveEdit` skips calling `updateWorkoutDurationWeeks` entirely when locked (so re-saving the same already-set value never hits the guard's rejection — the guard exists to stop an actual *change*, not to make every save of an already-durationed workout fail). **The assign flow's own duration field is unaffected** — it's still freely editable up until "Assign" is tapped, since nothing has been saved yet; the lock only ever applies after a value has been committed once, whether that happened at assignment or in a later edit.
- **"Week X/Y" progress, computed the same way in two different places** (`getProgramWeekProgress(workout, atDate?)`, `workoutDuration.ts`) — which week `atDate` (default now) falls in relative to `created_at`, clamped to `[1, duration_weeks]`, `null` if `duration_weeks` isn't set:
  - **Trainee side (`WorkoutScreen.tsx`):** a `weekProgressBadge` pill in the **top-right** of the workout-detail header (`headerRow`, restructured from a plain stacked column into a row with the existing name/meta block on the left) — "{current}/{total}" over a small "WEEK" caption, in both the active-logging header and the read-only header, evaluated against *today* (the default `atDate`) so it advances on its own as real time passes, independent of anything the coach does other than having set `duration_weeks` in the first place.
  - **Coach side, in History specifically** (per feedback — "in coach section it would be for the history"), not the main workout list: `getTraineeHistory` (`db.ts`) now also selects `workouts(created_at, duration_weeks)` alongside the existing `name` join, returned as `workout_created_at`/`workout_duration_weeks` on each session. The Program tab's History sub-tab appends "· Week {current}/{total}" to a session's meta line, evaluated against **that session's own `completed_at`** (not today) — so a session from three weeks ago correctly shows the week it was actually done in, not the program's current week.
- **Which program week a mid-program *edit* landed in** — per feedback ("if it was an 8 week program and then the program was modified, then it should show that it will be for week 2"), distinct from the "Week X/Y" progress badge above (which just reads today's date, not when anything was changed). `workouts.exercises_updated_at` (migration: `scripts/workout_exercises_modified_week.sql`, nullable timestamptz) is stamped by `updateWorkoutExercises` (`db.ts`) every time a coach saves exercise changes to an already-assigned workout — deliberately **not** set by `createWorkout`, so a never-edited workout has `null` here and shows no "modified" badge at all, only ever a genuine post-assignment edit does.
  - **While editing** (`CoachTrainees.tsx`'s Edit Workout modal header): an `editingWorkoutWeek` memo runs `getProgramWeekProgress(workout)` (today's date, same as the trainee-side badge) against whichever workout is currently open, shown as "Editing in Week X of Y" right under the existing duration badge — so the coach sees, before saving, which week this change is about to be recorded against.
  - **After saving** (Program tab's workout list): once `exercises_updated_at` is set, the workout's row shows a "Modified in Week X of Y" tag — this time computed against **the saved `exercises_updated_at` timestamp**, not today, via the same `getProgramWeekProgress(workout, atDate)` helper (mirroring how the History tab's per-session week number works, above) — so the tag keeps reading "Week 2" indefinitely afterward, not drifting forward as today's date advances past week 2.
### Per-Set Exercise Targets (`exercises.set_details`)
Per feedback ("want to have separate lines for each set, so have set 1, reps, weight, time, rest (secs) and then have a button to add set"): a coach assigning/editing a trainee's workout can now give each individual **set** of an exercise its own reps/weight/time/rest target, instead of one shared reps/weight/time/rest applied to every set. E.g. set 1 can be a lighter warm-up, sets 2-3 the real working weight.
- **Schema** (`scripts/exercises_set_details.sql`, already run): `exercises.set_details jsonb`, nullable, additive. **Scoped to `exercises` (the per-trainee instance table) only — deliberately NOT `program_exercises` (the coach's reusable templates).** Templates stay at the simpler "N sets of X reps" level; per-set customization is a per-trainee, at-assignment/edit-time concern, same scoping logic as `duration_weeks` above.
- **Backward-compatible by construction, not by special-casing:** `sets`/`reps`/`weight`/`time`/`rest_seconds` are kept in sync as a single-value summary whenever `set_details` is used — `sets` = array length, the other four = the first set's values. Every existing read site (coach's collapsed workout-row summary, `exercise_weight_logs`, legacy exercises assigned before this feature) keeps working unchanged whether or not a given exercise actually has per-set detail. `null`/absent `set_details` means "not using this yet," not "no exercise" — `CoachTrainees.tsx` falls back to expanding the scalar columns into N identical rows in that case.
- **`CoachTrainees.tsx` (both the "Assign New Workout" step 2 builder and the Edit Workout modal):** `ExerciseEntry.setRows: SetRow[]` replaced the old single shared sets-count/reps/weight/time/rest fields. Each exercise renders one row per set ("SET 1", "SET 2", ...) with its own REPS/WEIGHT/TIME/REST(SECS) fields, a per-set remove button (shown only when >1 set), and an "Add Set" button below the set list that duplicates the last row's values as a starting point for the new one. `expandToSetRows(count, reps, weight, time, restSeconds)` builds N identical `SetRow`s from a template/legacy exercise's scalar values (used by `selectProgram`'s pre-fill and `openEditModal`'s fallback); `exerciseEntryToPayload(entry)` is the reverse — collapses `setRows` back into the scalar-summary + `set_details` array shape `ExercisePayloadEntry` expects. `openEditModal` prefers an exercise's real `set_details` when present/non-empty over re-deriving from the scalars.
- **`syncExerciseRows` (`db.ts`)** already forwarded arbitrary payload properties generically via `{...rest}` — no changes needed there for the new field to flow through; it's simply present on `exercises`-table payloads and absent on `program_exercises`-table payloads, since only `CoachTrainees.tsx`'s code path ever constructs it.
- **Trainee side (`WorkoutScreen.tsx`):** `buildInitialExercises` prefers `ex.setDetails` (mapped 1:1 into that exercise's `SetLog[]`) when present/non-empty, falling back to repeating the scalar reps/weight N times otherwise — the trainee's per-set logging table (`SetLog[]`, already per-set structured for logging actual reps/weight/effort) needed no rendering/column changes, only this population-source change.
- **Deliberately out of scope for this pass:** per-set TIME/rest-timer behavior isn't varied per individual set boundary on the trainee UI — the rest timer and `coachTime` display still use the first set's `time`/`rest_seconds` (i.e. the scalar-summary columns), not a per-set countdown that changes mid-exercise. Not the reusable Program-template builder (`CoachPrograms.tsx`)/`program_exercises` — see Schema above.

Purely visual — no change to the underlying state, validation, or `updateProfile` save flow.

## Coach ↔ Trainee Connection

Replaces the old "coach unilaterally assigns" flow entirely.

- `coach_requests` table: either side can initiate (`initiated_by: 'coach' | 'trainee'`), the other side accepts/declines.
  - Trainee side: `ProfileScreen.tsx` → "Find a Coach" search modal (only shown when no coach assigned) → send request. Incoming coach-initiated requests show as an accept/decline card at the top of the Coach card.
  - Coach side: `CoachTrainees.tsx` → "Find Trainees" search modal → send request. Incoming trainee-initiated requests show in a "Requests" section with accept/decline.
- **Sending a trainee-initiated request notifies the coach** — `sendCoachRequest` (db.ts) sends an in-app message (`👋 {name} wants to connect with you as their coach`) through the same mechanism as the workout-completion notification, so it lights up the coach's notification bell instead of sitting silently until they happen to check the Requests section. Only that direction — a coach-initiated request doesn't yet notify the trainee (wasn't asked for; the trainee still only sees it passively as a card).
- **A trainee can cancel their own outgoing request** — once sent, `ProfileScreen.tsx`'s Coach card shows a "Cancel Request" button beneath the "Request sent — waiting for approval" row (`handleCancelRequest`, only rendered/relevant while `outgoingRequest` is set). Reuses `declineCoachRequest(requestId)` — the same function a coach uses to reject an incoming request — since `getOutgoingCoachRequestForTrainee` only ever returns `status: 'pending'` rows, marking it `'declined'` is functionally identical to deleting it from this screen's perspective, and it also frees the trainee to immediately search and request a different (or the same) coach again (`getCoachRequestStatus` treats `'declined'` as `'none'`).
- Accepting calls `acceptCoachRequest(requestId, coachId, traineeId)` → sets `coach_id` + `status: 'assigned'` (same effect the old direct-assign had).
- Once connected, the coach can then assign a Program (which creates the trainee's `workouts` row from a template) via `CoachTrainees.tsx`'s trainee-detail modal.
- `CoachDashboard.tsx` shows real quick stats (trainee count, program count, 7-day compliance %) and a trainee preview list with a "Find Trainees" shortcut when empty.

## Multiple Workouts Per Trainee

Previously a trainee could only ever have one workout — `getWorkoutWithExercises(traineeId)` always fetched the single latest `workouts` row, and assigning a new program silently superseded whatever came before. This is now a genuine multi-workout model:

- **Schema:** `workouts.active` (boolean, default `true`) and `workouts.end_date` (date, nullable) — a coach retires a workout by toggling it inactive rather than deleting it, so it stays visible as history; `end_date` auto-stamps to today when deactivated (and clears if reactivated), so a coach can see how long it actually ran. Migrations: `/private/tmp/scratch/workouts_add_active_flag.sql`, `/private/tmp/scratch/nutrition_templates_and_workout_enddate.sql` (both already run).
- **Schema:** `workouts.scheduled_days` (`smallint[]`, nullable) — weekday numbers (0=Sunday..6=Saturday, matching JS `Date.getDay()`) a coach restricts a workout to; null/empty = no restriction, any day. Migration: `/private/tmp/scratch/workout_scheduled_days.sql` (already run).
- **`db.ts`:** `getWorkoutWithExercises` now takes a **`workoutId`**, not a `traineeId` — it fetches one specific workout, since "the latest one" is no longer a meaningful concept. `getWorkoutsForTrainee(traineeId)` returns *all* of a trainee's workouts (active + inactive), newest first. `setWorkoutActive(workoutId, active)` toggles the flag and stamps/clears `end_date`. `updateWorkoutScheduledDays(workoutId, days)` — empty array is stored as `null`. `createWorkout` always inserts with `active: true`; `scheduled_days` is optional (defaults `null`). `deleteWorkout(workoutId)` — refuses (friendly error) if any `workout_sessions` row references it, since that would orphan completion history; otherwise deletes its `exercises` rows then itself. `getWorkoutIdsCompletedToday(traineeId)` returns workout ids with a session logged since the device's local midnight — **scoped to today only**, not all-time (an earlier version, `getCompletedWorkoutIds`, locked a workout forever after one completion; corrected per feedback — "once a day" meant a daily reset, not a permanent one-time lock).
- **A workout locks for the rest of today once completed, then reopens tomorrow** — enforced by `getWorkoutIdsCompletedToday`, not a permanent flag. Separately, **a coach can restrict a workout to specific weekdays** (`scheduled_days`) — e.g. a "Leg Day" workout set to Mon/Thu only won't show as doable on other days, independent of the daily completion lock.
- **`CoachTrainees.tsx` (coach side):** the trainee-detail modal's "Program" tab is a list of every workout ever assigned, each an expandable row (tap to load its exercises on demand) with an **Edit** button, an **Active/Inactive `Switch`** (toggling off shows "Ended {date}" in the row), and a **delete** (trash) button guarded by `deleteWorkout`'s history check. The row's meta line always shows `scheduledDaysLabel(w.scheduled_days)` ("Any day" or e.g. "Mon, Wed, Fri"). Both the assign flow (step 2 "Build Workout") and the edit-workout modal have a 7-chip weekday picker ("SCHEDULED DAYS (OPTIONAL)") — `DAY_ABBR`/`toggleDay`/`scheduledDaysLabel` helpers, `dayChip`/`dayChipActive` styles. "Assign New Workout" in the status row is always available and always *adds*. The roster card shows each trainee's active-workout count (`traineeActiveCounts`, batch-fetched in `loadData`) instead of a single program name.
- **`WorkoutScreen.tsx` (trainee side):** the tab's landing view is a workout picker with **four** sections — "To Do" (active, scheduled for today or unrestricted, not completed today — tappable, starts logging), "Completed Today" (active, completed today — tappable, read-only, checkmark icon, reopens tomorrow), "Not Today" (active, `scheduled_days` set but today isn't in it — tappable, read-only, calendar icon, shows which days it *is* scheduled for), and "Past" (inactive — tappable, read-only, archive icon). `readOnlyReason` (`'inactive' | 'completed' | 'notToday' | null`) drives which banner/label text shows; `isScheduledForToday()` and `scheduledDaysLabel()` are local helpers mirroring the coach-side ones. Selecting a workout shows a "‹ All Workouts" back row to return to the picker. `submitted`/exercise-log state resets per selected workout via a `useEffect` keyed on `selectedWorkoutId`; finishing also immediately adds the id to local `completedTodayIds` so the picker reflects the lock without waiting for a refetch (it'll drop out of that set again on the next day's fetch).
- **`TrainerDashboard.tsx` (Home) had a workout preview card** (fetched via `getWorkoutsForTrainee`/`getWorkoutWithExercises`, previewing the most recent active workout's top 3 exercises) that was **deliberately non-interactive** — an earlier version made the whole card tappable to jump to the Workout tab, but that read as misleading since tapping it silently launched the workout-picker flow, so it was reverted to a plain preview. Per later feedback that a non-tappable card reads as broken/dead UI rather than "intentionally informational," **it — along with the Weekly Performance bar chart card and the bottom Workouts/Day Streak/Total XP row — was removed from Home entirely**, not just made passive.
- **A "Workout Today" card was later added back to Home**, positioned above Calories Today — unlike the old preview card, this one *is* genuinely actionable: it lists every active workout scheduled for today (via `isScheduledForToday`) that hasn't already been completed today (`getWorkoutIdsCompletedToday`), and each row is tappable. Tapping deep-links into the Workout tab and opens that specific workout directly (`navigation.navigate('Workout', { openWorkoutId })`, read by `WorkoutScreen.tsx` via a `useRoute`/`useNavigation` effect that sets `selectedWorkoutId` then clears the param — same pattern `CoachDashboard` uses for `openTraineeId` → `CoachTrainees`). The card only renders when there's at least one such workout; it's absent otherwise rather than showing an empty state. Home's cards, top to bottom: header, Gamification Hero (level/XP bar/streak), Workout Today (conditional), Calories Today, Today's Activity (steps/weight/water).
- **Heart rate was removed from Today's Activity per feedback** — "not in use yet." The stat tile, the "LOG HEART RATE" input row, and the underlying `hrInput`/`savingHr`/`handleSaveHeartRate` state in `TrainerDashboard.tsx` are all gone. `setTodayHeartRate` (`db.ts`) and `heart_rate` on the `TodayVitals`/`vitals` shape are left in place, untouched, since this may come back later — don't reintroduce the UI without checking whether it's wanted again first.
- **`TrainerDashboard.tsx`'s "Calories Today" card was previously 100% hardcoded** — `—`/"not synced"/"Synced by your coach"/a permanent 0%-width bar, regardless of any real plan or logging — a leftover from before nutrition tracking existed for trainees. Now wired to the same source as `FoodLogScreen.tsx`'s Nutrition tab (see below): today's calories (manual `food_log_entries` + `sumTodayAsPlannedNutrition(...).calories`) against the active plan's `target_calories`, a live-filled progress bar, and the plan's target macros. Honest empty state — "No active nutrition plan" — when there isn't one, instead of the old fake "not synced". **Color-coded per macro, mirrored identically on both `TrainerDashboard.tsx` (Home) and `FoodLogScreen.tsx` (Nutrition tab → "Nutrition" segment):**
  - **Every bar (calories + all three macros) is an `{consumed} / {target}` reading over a `DualBar`** — a two-segment progress bar (local helper, duplicated per-file same as the rest of this card) that fills `colors.success` (green) up to the target on **all four bars**, then — only if over — keeps going in `colors.primary` (red) for the overage amount. All four bars share the same green base deliberately (not each macro's own color) — an earlier version gave protein a red base to match its label, which made a red overflow segment invisible against an already-red bar; green-always-under, red-always-over is the one scheme that reads unambiguously on every bar. `DualBar`'s track width is `max(consumed, target)`, so the base segment shrinks proportionally as the red overage grows, and the two always sum to a full bar.
  - **The `{consumed}/{target}` number text is always plain grey (`colors.textSecondary`)**, on all four rows including calories — it never recolors on over/under; only the bar itself carries that signal. The **macro label word** ("Protein"/"Carbs"/"Fat", not the number, and not the bar) is colored instead — protein `colors.primary` red, carbs `#4A9EFF` blue, fat `colors.gold` yellow — purely to tell the three macro rows apart at a glance, independent of the (always-green/red) bar beneath it.
  - **Protein/Carbs/Fat:** three more bars below the calorie bar, only rendered for whichever targets are actually set. "Consumed" comes from `sumTodayAsPlannedNutrition` (`src/lib/nutritionCalc.ts`), which sums `actual_protein/carbs/fat` off today's "As Planned" meal completions — manual `food_log_entries` only ever carry a calorie figure, no macro breakdown, so these three bars reflect planned-meal tracking only, not ad-hoc manual entries.

## Shared Exercise Library

- `exercise_library` table, global — seeded with the original 22 default exercises (Push/Pull/Legs/Core). Since renamed/extended: `Leg Curl` → `Knee Extension`, plus a new `Knee Curl` added.
- **Any coach** can add/edit/delete library entries — deliberately *not* admin-gated (Admin's role per the top-level spec is scoped to third-party sync only, not templates; the whole DB already follows an "any coach manages their own stuff" model with no role-based restrictions).
- `ExerciseLibraryManager.tsx` — full-screen modal: list grouped by category, add/edit/delete. Reachable via "Manage Library" next to "Suggested Exercises" in the Add/Edit Program modals.
- Categories are **dynamic** — derived from whatever categories exist in the library, unioned with a hardcoded `known` list (`['Push','Pull','Legs','Core','Cardio','Stretch']`, duplicated identically in `ExerciseLibraryManager.tsx`/`CoachPrograms.tsx`/`CoachTrainees.tsx` — always shown even with zero exercises yet, so a coach can still pick one to add the first exercise into it) — not a hardcoded *exercise* list, a coach can still type a brand-new category name directly in the add/edit form and it becomes real the moment any exercise uses it.
- Both `CoachPrograms.tsx` and `CoachTrainees.tsx` pull their "suggested exercises" picker from this shared library — there is no more per-file hardcoded exercise list.
- **`scripts/exercise_library_full_catalog.sql`** seeds ~647 more named exercises across 20 muscle-group/training-type categories (Chest, Back, Shoulders, Biceps, Triceps, Forearms and Grip, Quadriceps, Hamstrings, Glutes, Calves and Shins, Abdominals and Core, Hip Adductors and Abductors, Compound Full-Body, Bodyweight and Calisthenics, Cardio, Functional Training and Conditioning, Olympic Lifting and Power Training, Smith Machine Exercises, Cable Machine Exercises, Stretching/Mobility and Recovery) — a user-provided list, generated into SQL by a one-off script rather than hand-typed, to avoid transcription errors at that volume. These are new categories alongside the original Push/Pull/Legs/Core/Cardio/Stretch ones, not a replacement — existing exercises/programs referencing the old categories are untouched.
  - **The same exercise name intentionally appears under more than one category** where it genuinely belongs to more than one (e.g. "Pull-up" under Back, Biceps, *and* Bodyweight and Calisthenics; "Romanian deadlift" under both Hamstrings and Glutes; several "Smith machine X" / "Cable X" variants appear both under their muscle-group category and again under the dedicated Smith Machine/Cable Machine equipment categories) — each is its own row, since `category` is single-valued per row and a coach browsing by category should find the exercise there regardless of which lens they're browsing by.
  - **`default_sets`/`default_reps`/`default_time` are per-category starting suggestions, not per-exercise prescriptions** — same role as the library's original seeded defaults. A coach still edits these per trainee/program when actually assigning; this just avoids leaving ~647 new rows with meaningless all-zero defaults. `default_weight` is left null throughout (real load is always coach-entered; several categories — bodyweight, cardio, stretching — have no weight at all).
  - **Idempotent via a new `(name, category)` unique index**, not just an `on conflict`-free plain insert — safe to re-run. This is a new constraint the live DB didn't have before (nothing previously inserted the same name under two different categories, so nothing could have collided) — flagged in case anything about it ever needs reverting, though there's no reason to expect it would.
- **With ~650 exercises now in the library, two UI spots that used to render every exercise flat and always-visible needed to become search/collapse interfaces instead — reported as "can't see the exercises":**
  - **The "Suggested Exercises" picker** (`CoachPrograms.tsx`'s Add/Edit Program, `CoachTrainees.tsx`'s assign-workout step 2 and Edit Workout modal — 4 call sites total) used to be a category chip row + a flat wrapped grid of every exercise chip in the active category below it; some categories now have 30–57 exercises, which just doesn't work as an always-expanded grid. Replaced with a single tappable field ("Choose a {category} exercise (N)…") that opens a searchable dropdown modal instead.
    - `CoachPrograms.tsx` already had exactly this kind of modal (`openNamePicker`) for a *different* purpose — renaming an already-added exercise row's name — so it was extended rather than duplicated: a new optional `isAdded: (name: string) => boolean` param (only the "add suggested" call sites pass one; the rename call sites still don't, since "already added" isn't meaningful there) shows a checkmark and disables re-adding an already-present exercise, same as the old chips did.
    - `CoachTrainees.tsx` had no equivalent picker at all (its own exercise-name field is a plain free-text `TextInput`, never a dropdown) — built one from scratch, one shared modal + state used by both of this file's two "Suggested Exercises" sections, parameterized by category/onSelect/isAdded the same way. Needed the same nested-modal fix as every other case of this in the file (Robustness Pitfalls #7): the Assign/Edit Workout modals' own `visible` prop is now gated on `!showExercisePicker` too, not just their own flag — simpler than that pitfall's usual capture-and-restore dance since neither flag itself ever changes while the picker is open, only the resulting `visible` boolean does.
  - **Category selection moved from an always-visible chip row on the main screen into the picker modal itself**, in both `CoachPrograms.tsx` and `CoachTrainees.tsx` — reported as "I can scroll across the different categories [on the main screen], can you turn this into a category which then filters the search exercises [inside the picker]". The outer `categoryRow` `ScrollView` next to each "Suggested Exercises" field is gone; category selection now lives inside the picker modal, above the search input, and tapping/picking a category there both filters the list below it and syncs back to the screen's `activeCategory`/`editActiveCategory` state (`handleNamePickerCategoryChange` / `handleExercisePickerCategoryChange`, tracking which of add-vs-edit opened the picker via a `which` ref/param so it syncs the right piece of state). The picker's title simplified from "Select {category} Exercise" to plain "Select Exercise" since the category field now shows it directly.
    - **Inside the modal, category itself is a dropdown, not a chip scroll** — a follow-up report ("the exercise group should be a drop down list") pointed out that scrolling through a *horizontal row* of ~20 category chips (even moved inside the modal) was still the same underlying problem as the "can't see the exercises" bug above, just one level in. Replaced with a single tappable field (icon + current category name + chevron) that expands an inline vertical list directly below it (`showNamePickerCategoryList` / `showExercisePickerCategoryList`) — collapses again once a category is tapped, or whenever the picker modal itself closes. Deliberately an inline expand, not a second nested `Modal` (Robustness Pitfalls #7).
    - **Both picker modals' `KeyboardAvoidingView` used `behavior={Platform.OS === 'ios' ? 'padding' : undefined}`** — `undefined` disables keyboard avoidance entirely on Android, which is almost certainly what the coach meant by "keyboard issues again, where the keyboard takes up the entire screen": typing into either picker's search field on Android, nothing pushed the input above the keyboard. This app's own larger Add/Edit Program and Assign/Edit Workout modals already used `'height'` on Android successfully, so both pickers were changed to match (`'height'` instead of `undefined`) — scoped to just these two, since several other small bottom-sheet modals elsewhere in the app (Find Trainees, Find Friends, Create Gym, Add Member, chat modals) still use `undefined` deliberately/untested and are out of scope for this fix.
  - **`ExerciseLibraryManager.tsx`'s own category list** (the "Manage Library" screen) used to render every exercise in every one of the now-26 categories flat and always-expanded in one long `ScrollView` — categories now **collapse by default** (`expandedCategories: Set<string>`, toggled by tapping the header), showing just the category name + a `(N)` count until tapped open. The header's old behavior (tap to open the add-exercise form pre-filled with that category) moved to a small dedicated "+" button on the right of the row, since the header itself is now the expand/collapse toggle.
- **Per-exercise "Single Arm" / "Single Leg" marker** (`laterality: 'single_arm' | 'single_leg' | null`, null = both sides together) — a coach building a Program template (`CoachPrograms.tsx`) or a trainee's Workout (`CoachTrainees.tsx`) can tag an exercise as done one side at a time. Added to both `program_exercises` and `exercises` (same pattern as every other shared field — name/sets/reps/weight/time/rest_seconds — that exists on both tables), via `scripts/exercise_laterality.sql` (**not yet run** — needs the user to run it in the Supabase SQL Editor before this field actually persists). It's a whole-exercise property, not per-set, so in `CoachTrainees.tsx`'s per-set-row builder it lives on `ExerciseEntry` itself (not `SetRow`) and the toggle renders once per exercise card, not once per set row. ## Nutrition Plans & Food Log

A "Diet Plan" feature was briefly built as a separate table/tab from the existing PDF-based "Nutrition Plan" feature, then **merged into one concept** per explicit feedback — a diet plan and a nutrition plan are the same thing, and "nutrition" is the preferred term throughout the UI. Not third-party synced data, so it doesn't fall under the root `CLAUDE.md`'s "Admin-only third-party sync" restriction; it follows the same coach-assigns/trainee-logs pattern already established for workouts.

- **Schema:** `nutrition_plans` (per-trainee instances) carries both the original PDF fields (`file_name`/`file_url`/`storage_path`, all nullable — not every plan has a document) and structured fields (`title` not null, `notes`, optional `target_calories`/`target_protein`/`target_carbs`/`target_fat`/`target_water_ml`, `active` boolean default true, `template_id` nullable FK). **A trainee can have several nutrition plans** — some active, some inactive — mirroring `workouts.active` exactly. Migrations: `/private/tmp/scratch/merge_nutrition_diet_plans.sql`, `/private/tmp/scratch/nutrition_templates_and_workout_enddate.sql` (both already run). `target_water_ml` mirrors the other targets exactly (same column on both `nutrition_plans` and `nutrition_plan_templates`) — it's a coach-set daily *goal*, distinct from the `vitals` table's `water` metric (what the trainee actually logged that day).
- **Reusable templates (`nutrition_plan_templates`) — mirrors Programs → Workouts exactly.** A coach sets up a plan once (title, target macros, notes) as a template, then *assigns* it to any number of trainees; assigning copies the template's current values into a new `nutrition_plans` row (`template_id` kept only for provenance) — same snapshot pattern as assigning a Program copies its exercises into a `workouts` row, so later template edits don't retroactively change plans already handed out. This replaced an earlier per-trainee "New Plan" custom-build flow, which didn't match how the rest of the app's coach-authored content works (see Programs).
- **`db.ts`:** `getNutritionTemplates`/`createNutritionTemplate`/`updateNutritionTemplate`/`deleteNutritionTemplate` (template CRUD), `assignNutritionTemplate(traineeId, coachId, template)` (the copy-on-assign function), `getNutritionPlans` (all of a trainee's assigned plans, unchanged), `uploadNutritionPlan` (PDF-only quick add, sets `title` to the filename, no template), `updateNutritionPlan` (edits an assigned plan's copied values), `setNutritionPlanActive`, `deleteNutritionPlan`.
- **New top-level coach tab: "Nutrition"** (`CoachNutritionTemplates.tsx`, in `CoachTabs.tsx` between Programs and Trainees) — list/add/edit/delete templates, mirrors `CoachPrograms.tsx`'s structure (no exercises to manage, just title/notes/targets, so no library/name-picker complexity). Deleting a template does **not** touch trainees already assigned a copy of it (`ON DELETE SET NULL` on `template_id`).
- **Trainee-detail modal tab order (`CoachTrainees.tsx`):** Program, **Nutrition**, Weight, Steps, Chat (`detailTab` array) — Nutrition sits right after Program per feedback; don't reorder back to the old Program/Weight/Steps/Nutrition/Chat sequence.
- **Per-trainee assignment (`CoachTrainees.tsx`):** the trainee-detail modal's "Nutrition" tab is split into a **Plans / History** segmented toggle (`nutritionSubTab`, hidden while the inline plan editor is open). "Plans" is an expandable list (same pattern as the Program tab's workout list) with Edit/Active-toggle/Delete per plan, and two actions up top: "Assign Plan" (opens a picker of the coach's templates — tap one to assign) and "Build Calorie Plan" (opens the calculator — see below). **The old "Upload PDF" quick-add entry point was removed per feedback** — `uploadNutritionPlan` (db.ts) still exists and PDF display (`plan.file_url`/`file_name`, tappable to open) is untouched, but there's no button that calls it anymore; a coach now always goes through a template or the calculator. The old ad-hoc "New Plan" (build from scratch, no template) button was already gone before this. The manual per-plan editor (opened via Edit) has DAILY TARGETS fields for calories/protein/carbs/fat plus a WATER (ML) field (`planWater` state, saved/loaded alongside the others) — all optional. The expanded plan detail view shows a target chip per set field, including water (`{target_water_ml}ml`), and — when the trainee has an active plan with a water target set — a "{today's actual} / {target}ml water today" summary chip above the existing per-day water-intake log, computed from that day's `vitals` row (`selectedTraineeWater[0]`, only counted if its `created_date` is today).
  - **"History"** (new) mirrors the trainee's own Nutrition tab History segment (`FoodLogScreen.tsx`) for the coach: `buildTraineeFoodHistory` pools every plan's meal-tracking (As Planned/Substituted/Skipped) via `planCompletions` — now **eagerly fetched for every plan with meals** as soon as a trainee is selected (`Promise.all` over `getMealCompletions` per plan, right after the main detail-load `Promise.all`), not just the one plan the coach happens to expand — plus the trainee's manual `food_log_entries` (`selectedTraineeFoodLog`, fetched alongside the rest of the detail data via `getFoodLogEntries`), merged into one by-date timeline (today's meal-tracking excluded, same convention as the trainee side; food log entries aren't, since there's no separate "today" view for those on the coach side either). This sits alongside — doesn't replace — each individual plan card's own "ADHERENCE HISTORY" (still there, still per-plan-only), giving the coach a combined view without needing to open every plan.
  - **Water Intake also lives under "History", not "Plans"** — per feedback, it's a record of what the trainee actually drank (real logged history), not plan-management content, so the water target chip + per-day log (previously always shown above both segments) moved to sit above "FOOD LOG HISTORY" inside the History branch instead.
- **A trainee can have one active plan of each *kind* at once, and plan names must be unique per trainee.** A plan's kind is derived purely from `template_id`: non-null (`assignNutritionTemplate`) = a **Nutrition Plan**, null (`uploadNutritionPlan`, `createCalculatedNutritionPlan`) = a **Calorie & Macro Plan**. Originally a trainee could only ever have *one* active plan total, of either kind — changed per feedback, since a coach-assigned Nutrition Plan and a calculator-built Calorie & Macro Plan are conceptually independent and a trainee reasonably has both going at once. Both rules live in `db.ts`, applied uniformly across all three creation paths plus renaming (`updateNutritionPlan`) and the active toggle (`setNutritionPlanActive`) — not just one entry point:
  - `assertUniquePlanTitle(traineeId, title, excludePlanId?)` throws a friendly `Error` (surfaced via `Alert.alert(e.message)` at each call site) if the trainee already has any plan — active or past, either kind — with the same title (trimmed, case-insensitive). Scoped per-trainee, not per-coach, so different trainees reusing a common name like "Cutting Phase" is fine. **Unchanged by the kind split** — a Nutrition Plan and a Calorie & Macro Plan still can't share a name.
  - `deactivateOtherPlans(traineeId, exceptPlanId, isCalculated)` runs after every successful create, and inside `setNutritionPlanActive` when reactivating a past plan — sets every other currently-active plan **of the same kind** (`template_id` null vs. non-null, filtered via `.is()`/`.not()`) for that trainee to `active: false` and stamps `end_date` to today (new `nutrition_plans.end_date` column, migration `/private/tmp/scratch/nutrition_plans_end_date.sql`, mirrors `workouts.end_date`/`setWorkoutActive` exactly, including "reactivating clears it"). So assigning a new Nutrition Plan only retires the previous *Nutrition Plan*, and building/reactivating a Calorie & Macro Plan only retires the previous *Calorie & Macro Plan* — the other kind's active plan is untouched. Retired plans become visible as history (`!plan.active`, `end_date` set) in both the coach's plan list (`CoachTrainees.tsx`, shows "· Ended {date}" next to Created) and the trainee's own Nutrition tab ("· Ended {date}" line, `FoodLogScreen.tsx`).

  - **Target display when both kinds are active:** `TrainerDashboard.tsx`'s Home calorie card, `FoodLogScreen.tsx`'s Nutrition segment, and `CoachTrainees.tsx`'s Nutrition → History water chip all used to just `.find()` the (only ever one) active plan with a target set. ## Workout Completion Flow

Fully reworked — no more partial-save/resume semantics.

- **Single "Finish" button** (not "Finish Early" / "Complete Workout!"). Visible until the trainee taps it, then permanently hidden — no re-appearing, no "Reset Workout" (each day gets a fresh assigned workout, so resuming doesn't apply).
- Tapping Finish is **terminal**: it saves the session with whatever progress was logged (`progress = setsWithEffort / totalSets`), regardless of whether every exercise was checked off.
- On finish, `WorkoutScreen.handleSubmit` calls `completeWorkoutSession(...)` (db.ts → `complete_workout_session` RPC), which atomically: saves the session (including its real server-measured `duration_minutes`), recomputes and persists the streak, evaluates achievements, and writes whatever XP those achievements earned (nothing else — see "XP & Leveling System" below) to `users.xp`/`level`.
- Also auto-sends a message to the trainee's coach (see Coach Notifications below) — no XP/points mentioned at all, per feedback that coaches don't need score detail, just that the client did the work.
- Workout count on dashboards is derived live from `workout_sessions` rows — no separate counter needed.

## XP & Leveling System

**XP comes from the achievement list ONLY — nothing else, per explicit feedback.** This replaced an earlier model (still visible in git history, not in the current code) that also granted flat non-achievement XP: `WORKOUT_COMPLETE_XP` (+10 every finish regardless of achievements), a duration bonus (+2 per 10 min elapsed), `DAILY_STREAK_XP` (+2 for the first completion of a day), and `INVITE_FRIEND_XP` (+2 to whoever sent an accepted friend request). All four are gone — removed server-side in `scripts/xp_from_achievements_only.sql` (`complete_workout_session` and `accept_friend_request`), not hidden behind a flag. **A workout that doesn't newly earn any achievement now legitimately awards 0 XP** — that's correct, not a bug; don't reintroduce a participation-trophy flat bonus "to make 0 feel less bad."
- Session `duration_minutes` is still computed and persisted (still real, server-measured from `workout_session_starts`, never a client-reported number) — it's not XP anymore, it's an *input* several achievements need (Long Haul, 100/250 Hours, The Century Club (Time)). Don't conflate "we still compute this" with "this still grants XP."
- `users.streak` is still recomputed and persisted every completion too, same reasoning — several achievements key off it (3/7/14/21/30-Day Streak etc.), it's just not an XP source on its own anymore.
- See the Medals section below for which 55 achievements are actually automated and what each one's XP value is (`medal_xp_rewards`, rebuilt from the user-provided list — not the old 10/15/20/30/50 tiers from the first two catalog passes).

### Streak (`users.streak`)

`recalculateStreak(traineeId)` (`db.ts`) recomputes the streak from scratch from full activity history every time, rather than incrementing a stored counter — a day counts as active if the trainee completed a workout (`workout_sessions`) **or** tracked any nutrition that day (`meal_completions`, or a `food_log_entries` row, if that entry point ever comes back — see 2.2 note on the manual "Add Food" removal). It's called from two places: workout completion (inside `complete_workout_session`, server-side) and `FoodLogScreen.tsx`'s `MealRow.handleSetStatus` (any meal marked As Planned/Substituted/Skipped, via the standalone `recalculate_streak()` RPC).

**A single active day is not shown as a streak.** Per feedback ("it's not a streak" for just one day), the streak computation counts consecutive active days ending today and returns `0` unless that count is `>= 2` — so day 1 shows `0`, day 2 (consecutive) jumps straight to `2`, day 3 to `3`, etc. A gap resets to `0`.

Running/distance-based rewards (per-km, personal speed records, marathon) from the original gamification spec are **deliberately out of scope** — the app has no GPS/distance tracking at all.

### Leveling — 10 named levels, then a formula

`src/data/mockData.ts`: `LEVEL_TITLES` (10 names, Rookie Mover → Apex Legend), `LEVEL_TABLE_CUMULATIVE` (hardcoded cumulative XP per level, `[0, 20, 56, 124, 228, 376, 576, 836, 1166, 1576]`), and `cumulativeXpForLevel(level)` / `computeLevelFromXp(xp)` / `getXpForNextLevel(level)` / `getCurrentLevelXp(xp)` / `getLevelTitle(level)`.

- **The spec's own stated formula (`20 * (Level-1)^1.5`) does NOT reproduce its own 10-level table past Level 3** — e.g. it gives 540 for Level 10, not the table's 1,576. The table's own per-level increments *are* internally consistent (they sum to its own cumulative totals exactly), so **the table is the source of truth for Levels 1–10**, hardcoded rather than formula-derived. Don't try to "fix" this by re-deriving Levels 1–10 from the formula — that was checked and rejected; the table is intentional.
- **Levels 11+** (past the named table) use the spec's formula for each additional level's *increment*, **anchored onto Level 10's real total (1,576)** rather than restarting from the formula's own raw absolute value. This matters: the raw formula alone gives only ~632 for "Level 11" — using it unanchored would mean a trainee jumps from Level 10 to **~Level 19 in a single instant** the moment they cross 1,576 XP (verified by computing it out — this was caught and explicitly rejected, not a hypothetical). The anchored version telescopes to `1576 + 20*(level-1)^1.5 - 20*9^1.5` — monotonically increasing, no jump, just a gentler curve than Levels 1–10 (e.g. Level 10→11 needs 92 XP vs. Level 9→10's 410).
- **Level titles beyond 10** are generic `"Level N"` — the spec only names 10 levels.
- `ProfileScreen.tsx` and `GamificationScreen.tsx` both use `getLevelTitle(level)` for the displayed title band — `ProfileScreen.tsx` previously **hardcoded** "New Adventurer" regardless of actual level (a pre-existing bug, fixed alongside this); `GamificationScreen.tsx` previously had its own inline 4-band title logic (5/10/20 thresholds, different names) — replaced with the shared helper so there's one source of truth.

## Live Updates App-Wide (`useLiveRefresh`) + Phone Notifications

Reported in stages: first the notification bells only updated after logging out and back in, or (trainee only) after switching tabs away and back; then, concretely, a coach assigning a workout for today didn't show up on the trainee's Home card even though the phone notification for it came through; then a completed workout didn't show up in either side's History. Root cause each time was the same: a screen's `loadX` only ever ran inside a `useFocusEffect`, which — correctly — only reruns on an actual focus *transition*. Sitting still on an already-focused screen, or an internal segmented-control toggle that doesn't trigger React Navigation's focus event at all, is not a focus transition, so nothing ever refetched. Per feedback ("make sure that all screens have a live update and are not delayed"), this was fixed once as a shared hook and then applied to every screen whose data another person (the coach, the trainee, or anyone else sharing leaderboard/gym data) can change.

### `src/lib/useLiveRefresh.ts`

`useLiveRefresh(callback, intervalMs = 15000)` bundles three triggers that every fixed screen now shares, replacing a plain `useFocusEffect(callback)`:
1. **On focus** — unchanged behavior, still correct for an actual nav transition (e.g. switching tabs away and back).
2. **A ~15s poll while mounted**, regardless of focus — this is the actual live-update mechanism; see "Why polling, not Realtime" below.
3. **Immediately on app foreground-resume** — React Native fully suspends JS timers while backgrounded (see the Robustness Pitfalls section's rest-timer note), so the poll alone doesn't fire a backlog on resume, it just silently stops ticking and picks back up later. Listens for `AppState`'s `'change'` event and fires an immediate reload the moment it flips to `'active'`, so returning to the app doesn't wait up to `intervalMs` for the first correct refresh.

**Why polling, not Realtime:** a Supabase Realtime `postgres_changes` subscription would update instantly instead of within ~15s, but needs the relevant tables added to Supabase's realtime publication (`alter publication supabase_realtime add table messages;`, etc. — a DB-side change this environment has no credentials to make) and its RLS-over-Realtime behavior confirmed actually working, neither of which could be verified here. Polling was the option that could be shipped and reasoned about with confidence; revisit with Realtime if the ~15s delay ever becomes a real complaint on a specific screen.

**Where it's wired in, and why each one qualified** (anywhere a screen shows data the *other* side of a relationship — or another user entirely — can change):
- `CoachDashboard.tsx` — the notification bell (unchanged logic, just the hook swapped in) and the main trainee-list/program-count/7-day-compliance loader (previously `useFocusEffect`-only), plus the per-trainee reply-chat thread while it's open (guarded no-op when no thread is open, mirrors `CoachTrainees.tsx`'s pattern below).
- `TrainerDashboard.tsx` (trainee Home) — `loadHome` (profile/weights/metrics/nutrition/**workouts** — the concrete "Workout Today" card bug), the coach chat thread/unread-dot data, the notification bell, and the incoming-coach-request check. All four used to be four separate hand-written focus+poll+AppState blocks; now four `useLiveRefresh` calls.
- `CoachTrainees.tsx` — the roster/requests loader (`loadData`, including its new-trainee-request `Alert` popup), **and** the selected trainee's full detail view (workouts/history/weights/steps/water/nutrition/food-log/messages) — this is the exact screen behind "the coach isn't able to see that it was completed in the history." The detail loader is split into an `isInitial` flag: the *first* load (right after selecting a trainee) still shows the loading spinner, but the live-refresh poll calls it quietly (`isInitial: false`) so an already-open detail view doesn't flash back to a spinner every ~15s.
- `WorkoutScreen.tsx` (trainee) — a **separate, simpler "quiet" reload** (`reloadWorkoutsQuiet`) layered on top of the existing focus-effect rather than replacing it: that original effect's `cancelled`-flag guard specifically protects the picker's very first load against a stale overwrite if the trainee navigates away again quickly, which a poll/resume-only addition doesn't need and shouldn't risk touching. Means the workout list briefly double-fetches on a real focus event (one from each effect) — a harmless redundant network call, not a correctness issue, traded deliberately for not disturbing a working race-guard.
- `ExerciseLogScreen.tsx` (trainee's own workout History segment) and `FoodLogScreen.tsx` (trainee's nutrition + History) — both already-real screens, previously focus-only (the Workout tab's History segment also remounts fresh on every segment switch, since `WorkoutTabScreen.tsx` conditionally renders rather than hides, so this mainly helps while sitting on History without switching away).
- `ProfileScreen.tsx` (trainee) — the Coach card (incoming/outgoing request, connection) and nutrition documents.
- `SocialScreen.tsx` (trainee) and `CoachRankings.tsx` (coach) — leaderboard/gym/friends data that changes from **other users'** actions entirely, not just a coach↔trainee pair. Both of these were on a plain mount-only `useEffect` before this pass — not even focus-based — the most stale pattern in the app. Both needed an `isInitial`/`hasLoadedOnce` guard (same shape as `CoachTrainees.tsx`'s detail view) so the live-refresh poll doesn't flash the full-screen loading spinner back on every ~15s.
- `GamificationScreen.tsx` (trainee's medal collection) — lower-risk (most medals are earned within the same session's own workout-completion flow, which already updates local state directly) but included for consistency.
- **Deliberately left on plain `useFocusEffect`:** `CoachSettings.tsx`'s own profile load — it's the coach's own name/email, which nothing but the coach's own edit elsewhere can change; polling it would just be wasted network calls for data that is never stale from another actor's action.

### Phone notifications — real OS notification banners, with an important scope caveat

`src/lib/restNotifications.ts` gained `notifyNewActivity(title, body)`, a generic version of the existing `notifyMedalsEarned` (same permission/channel plumbing, same immediate-fire `trigger: null`/`{channelId}` pattern, same Expo-Go-Android no-op guard). Both dashboards' notification loaders diff each fetch against a `seenNotificationIds` ref (`Set<string>`, `null` until the first load) — **the first load of a session records existing history silently** (no notification spam for stuff that was already sitting there before the app was opened this time); any id that shows up in a **later** fetch that wasn't already in the set is genuinely new since the last check, and fires one `notifyNewActivity` call. The trainee's incoming-coach-request check uses the same silent-first-load convention with a single id instead of a set (`seenCoachRequestId`, `undefined` until loaded). This covers all four originally-requested cases on both sides: a new chat message, a trainee accepting a request/invite, a trainee sending a request, and a trainee earning an achievement (coach's side — the trainee's own achievement notification is unchanged, fired instantly at the point of earning, not through this polling path) — all four already flow through the one `messages` table (see Coach Notifications below), so the generic diff-and-notify logic covers every one of them with no per-event-type code.

**This is a LOCAL notification fired by the app's own running JS, not true remote push.** It only fires while the app process is alive — foregrounded, or backgrounded-but-not-yet-suspended-or-killed by the OS — because that's what has to execute the polling/diff code that decides to fire it. It will **not** wake up or notify through a fully closed/killed app, which is what "push notifications" usually implies. Genuine remote push (so a killed app still notifies) would need: Expo push tokens collected and stored per user, and a server-side trigger (a Supabase Database Webhook or Edge Function reacting to new `messages`/`coach_requests`/`user_medals` rows) calling Expo's push API — real new backend infrastructure this project doesn't have, and which this environment can't deploy or test (no DB service-role access, no Edge Function deploy capability here). It's also untestable via Expo Go regardless — Expo Go removed remote-push support entirely as of SDK 53 (see Known Gotcha #10) — a genuine remote-push build would need a dev-client/EAS build to even try. Flagged here rather than silently built as something it isn't; revisit as its own project if a trainee/coach with the app fully closed needs to be reachable.

## Coach Notifications

No push notifications — in-app only, built on the existing `messages` table. Per explicit feedback, the coach's bell should light up (red dot) for exactly four trainee-side events — **a new chat message, a trainee accepting an invitation (either a direct connect request OR redeeming an invite code), a trainee sending a connect request, and a trainee earning an achievement** — and the dot should clear the moment the coach actually opens the bell, not before. The red-dot mechanics were already generic (`hasUnread = notifications.some(m => !m.read)`, cleared by `openNotifications` marking every unread row read — see `CoachDashboard.tsx`) from the first message type built; each event below just needed to actually write a `messages` row to light it up for that case too:
- Trainee finishing a workout auto-sends a message to their coach: `🏋️ {name} completed "{workout}" — {pct}% done`. **No XP/points ever mentioned** — per explicit feedback, a coach needs to know a client did the work (or, in the future, finished an eating plan), not their score. Was previously `..., +{xp} XP`; removed entirely rather than just hidden when `0` (see the XP rework in "Workout Completion Flow" above for why `0` became the common case).

Previously the request just sat silently in the "Requests" section of `CoachTrainees.tsx` with nothing surfacing it — a coach had no way to know one had arrived short of manually checking that tab. Isolated in its own try/catch so a notification failure never blocks the request itself.

  - `acceptCoachRequest(requestId, coachId, traineeId, initiatedBy)` (db.ts) gained a 4th param mirroring `sendCoachRequest`'s own — this function is called from both sides (a coach accepting a trainee-initiated request in `CoachTrainees.tsx`'s "Requests" section, or a trainee accepting a coach-initiated one in `ProfileScreen.tsx`/`TrainerDashboard.tsx`), but only the latter case needs a notification (a coach already knows when *they* click Accept). When `initiatedBy === 'coach'` (the request was coach-initiated, i.e. the trainee is the one accepting right now), it sends `✅ {trainee's name} accepted your coach request!` to the coach. After `redeem_trainee_invite` succeeds, it re-fetches the just-created profile (that RPC's own `INSERT` already set `coach_id` — re-reading it is cheaper than adding a return value to the RPC via a new migration) and sends `🎉 {name} joined using your invite code!` to that coach. Isolated in its own try/catch, same convention as every other notification call site in this file.
- `CoachDashboard.tsx` has a notification bell in the header with a red-dot badge; tapping opens a modal listing them.
- **Notifications persist** — `getMessagesForCoach(coachId)` fetches all messages to the coach (read + unread), not just unread (unlike the retired `getUnreadMessagesForCoach`, which made notifications vanish forever the moment they were marked read, since only the unread set was ever fetched). - Each notification row has a delete button (`deleteMessage(id)`) so the coach can clear old ones instead of being stuck with a growing list.

- Trainee's own chat button (`TrainerDashboard.tsx`) — the unread dot now only renders when there's a genuine unread message from the coach (`dbMessages.some(m => m.from_id === coachId && !m.read)`). It used to always render whenever a coach was assigned, regardless of unread state.

- **Online status is real**, via `useIsUserOnline` (`src/lib/presence.ts`) — was previously a hardcoded "● Online" regardless of whether the coach was actually using the app (an instance of the same "don't fabricate data that looks real" issue as the old fake admin dashboard stats). Shows "Offline" (not just hidden) when false — an honest state, not an absence of one.

### Coach → Trainee
- Coaches can now reply/initiate: `CoachDashboard.tsx`'s notification-triggered reply modal, and a dedicated "Chat" tab in `CoachTrainees.tsx`'s trainee-detail modal for messaging any trainee proactively, not just in response to a notification.

### Online presence (`src/lib/presence.ts`)
- Real Supabase Realtime **Presence** (ephemeral, socket-based — not a DB table, no migration needed). `useTrackOwnPresence(userId)` is called once, in `RootNavigator.tsx`, for whichever role is logged in — marks that session online while the app is foregrounded (`AppState`-gated; backgrounding untracks immediately rather than waiting on a socket-drop timeout). `useIsUserOnline(targetUserId)` reports whether that specific user id is currently tracked.
- **Module-level singleton, not one channel per hook call.** Supabase's realtime client reuses the same channel *object* for a given topic name — a second independent `supabase.channel('online-users')` call (e.g. from `useIsUserOnline` mounted in some other screen) returns that same, already-subscribed channel, and calling `.on()` on it throws `cannot add presence callbacks for realtime:online-users after subscribe()`. Hit this for real once `useIsUserOnline` was used from a screen mounted alongside `useTrackOwnPresence`. Fixed by making `useTrackOwnPresence` the *sole* creator/subscriber of the channel (module-level `sharedChannel` var); `useIsUserOnline` never calls `supabase.channel(...)` itself, only reads `sharedChannel.presenceState()`, kept reactive via a plain `listeners` Set that `notify()`s on every presence sync/join/leave and on the tracked channel's own mount/unmount. Don't reintroduce a second `supabase.channel(ONLINE_CHANNEL)` call anywhere.
- Only wired up where it's actually shown: the trainee's "Message Coach" modal. Nothing else in the app currently surfaces an online indicator.
- **Caveat:** admin "Login as &lt;coach&gt;" impersonation (see root `CLAUDE.md`) tracks presence under the *admin's own* real `auth.uid()`, not the impersonated coach's id — so a trainee wouldn't see their coach as "online" while an admin is impersonating them. Not handled; edge case, admin-only.

### Chat keyboard-avoidance (all three chat UIs: `TrainerDashboard.tsx`'s "Message Coach" modal, `CoachDashboard.tsx`'s reply modal, `CoachTrainees.tsx`'s Chat tab)
`KeyboardAvoidingView`'s Android `'height'`/`'padding'` auto-behavior does not reliably compose with content rendered inside a `<Modal>`, and — this took several rounds of screenshot-driven debugging to pin down — a **`transparent` `<Modal>` on Android is fundamentally the wrong container for a keyboard-avoiding chat screen**: its native window appears to size itself off its direct child's own reported box, so *any* shrink of that box for the keyboard (a raw `marginBottom` on it, or an `onLayout`-driven explicit height further down that changes the tree's size) shrinks the whole native window, exposing the real screen behind it undimmed. Multiple margin/measurement variations were tried on the two small `transparent` sheet modals and each either left the message list collapsed or exposed the background.

**Fix that actually stuck: all three are now genuine full-screen (non-`transparent`) `<Modal>`s**, structured identically — `fullScreenContainer`/`fullScreenSheet` (`useSafeAreaInsets()` applied as manual `paddingTop`/`paddingBottom`, not `SafeAreaView`, per the existing "SafeAreaView unreliable inside a Modal" gotcha below) → a plain header row with a `closeBtn` → `KeyboardAvoidingView` (`behavior={Platform.OS === 'ios' ? 'padding' : undefined}`, `style={{flex:1}}`) → the message `ScrollView` given an **explicit computed height** (`chatAreaHeight - keyboardOffset - 64`, floored at 80) once the keyboard is open, `flex:1` otherwise → the input row. `useKeyboardOffset` (`src/lib/useKeyboardOffset.ts`) tracks real keyboard height via native events, Android-only. With no background screen left to expose, the whole "transparent Modal shrinks to content" failure mode is moot — don't reintroduce a `transparent` sheet-style modal for a chat screen; if a new one is ever needed, copy this full-screen shape from the start rather than re-deriving it.

**`onLayout` (for `chatAreaHeight`, the Android-only measurement above) must go on a plain `View` *wrapping* the `KeyboardAvoidingView`, never as a prop directly on the `KeyboardAvoidingView` itself.** Broke iOS specifically, the hard way: `KeyboardAvoidingView` relies on its own internal `onLayout` to track its screen position — `'padding'` behavior (what iOS uses) needs that to compute the right padding amount. A consumer-supplied `onLayout` prop passed straight to it silently replaces that internal handler (later JSX props win), breaking `'padding'` behavior entirely. This was invisible on Android, where `behavior={undefined}` makes `KeyboardAvoidingView` an inert passthrough that never needed its own `onLayout` anyway — so the bug shipped unnoticed until it was tested on iOS. Fix: `<View style={{flex:1}} onLayout={...}><KeyboardAvoidingView style={{flex:1}} behavior={...}>...</KeyboardAvoidingView></View>` — same measured height (both are `flex:1` siblings-in-effect at rest), but `KeyboardAvoidingView`'s own `onLayout` stays untouched. If a future chat-shaped modal needs this same measured-height technique, wire it this way from the start.

### `autoFocus` inside a `transparent` `animationType="slide"` Modal + `KeyboardAvoidingView` — another iOS-only race
Same root shape as the two notes above, found while chasing the exact same "can't see what I'm typing" symptom on iOS in **six other modals** that are all small `transparent` sheets with an `autoFocus`ed search/name `TextInput` (CoachTrainees' Find Trainees, CoachRankings' Create Gym and Add Member, CoachPrograms' exercise-name picker, SocialScreen's Find Friends, ProfileScreen's Find a Coach). Adding `KeyboardAvoidingView` alone (the earlier fix) did **not** resolve it on iOS, even after a reload — because `autoFocus` fires the keyboard the instant the `TextInput` mounts, which is *during* the Modal's `"slide"` animation, before `KeyboardAvoidingView` has a stable layout to compute `'padding'` against. Its first (and, since nothing re-triggers it, only) padding calculation comes out wrong.

**Fix, applied to all six:** drop `autoFocus` from the `TextInput`; give it a `ref` instead, and focus it from the `<Modal>`'s `onShow` prop (fires once the slide transition has actually finished) — `<Modal ... onShow={() => inputRef.current?.focus()}>`. Don't reach for `autoFocus` on a `TextInput` inside any `animationType="slide"` Modal in this app going forward — use this `ref` + `onShow` pattern instead, even for a modal that doesn't otherwise need `KeyboardAvoidingView` help.

Each of the three chats also needed its own `scrollToEnd` on the message `ScrollView` (via a ref, re-fires on new messages / keyboard open) — none of them auto-scrolled to the latest message before, it just never showed as a bug while the box was always tall enough to show everything unscrolled.

### iOS `'padding'` behavior itself turned out unreliable too, for the three chat screens specifically — confirmed via a live screenshot after the two fixes above
Even after fixing the `onLayout` hijack and the `autoFocus` race, a live iOS screenshot of `CoachTrainees.tsx`'s Chat tab still showed the keyboard fully covering the input row, blank gap and all — the same symptom, a third distinct cause. Best working theory: this `KeyboardAvoidingView` unmounts and remounts every time the trainee-detail modal's tab switches to "Chat" (it's one branch of a `detailTab === 'chat' ? (...) : (...)` conditional), and `'padding'` behavior's internal frame-tracking doesn't reliably settle in time on iOS across that remount, the same general shape of fragility as the other two `KeyboardAvoidingView` issues above, just a third manifestation of it.

**Fix: stopped depending on `'padding'` behavior on iOS at all for these three screens.** `useKeyboardOffset` (`src/lib/useKeyboardOffset.ts`) now tracks the real keyboard height on iOS too, via the exact same `keyboardDidShow`/`keyboardDidHide` event names Android already used — **not** `keyboardWillShow`/`keyboardWillHide`; an earlier version of this fix tried the `Will` variants on iOS (in principle they fire earlier, in sync with the keyboard's own animation) but that was an unproven code path that turned out not to fix anything, whereas `Did` is the pair already confirmed working. All three chat `KeyboardAvoidingView`s now use `behavior={undefined}` unconditionally (not `Platform.OS === 'ios' ? 'padding' : undefined`) — on Android this resolves to the exact same value as before (`undefined`), so **Android's behavior is untouched**; on iOS it now relies entirely on the same explicit-computed-height mechanism already proven working on Android (`chatAreaHeight - keyboardOffset - 64`), rather than any of `KeyboardAvoidingView`'s own built-in behaviors. If a `KeyboardAvoidingView` on either platform ever needs fixing again in this app, reach for this measured-height technique first rather than trying to coax `'padding'`/`'height'` into working — neither has held up reliably inside a `<Modal>` in this codebase, on either platform, across three separate root causes now.

### A fourth cause, on top of the other three — `<ScrollView style={{height}}>` silently ignores an explicit height in this exact nested context on iOS
Even with the real `Did`-event keyboard tracking and `behavior={undefined}` both correctly in place, the bug *still* reproduced on iOS. This one took a genuine multi-round debug pass (not guessing) to pin down: a temporary on-screen readout of the live `keyboardOffset`/`chatAreaHeight` values, rendered directly in the Chat tab and screenshotted with the keyboard open, proved the values themselves were correct (e.g. `kb=308 area=603`, giving a sane computed height of ~231) — but the message list still rendered at very close to its *full*, un-shrunk height regardless. First theory tried: the `ScrollView`'s `style` swaps between an object with `flex: 1` and one without, and iOS/Yoga doesn't reliably reset a stale `flex: 1` when the replacement object doesn't re-mention `flex` — so `flex: 0` was added explicitly. **That didn't fix it either.** Isolated further with a colored-border debug pass: a **hardcoded, unconditional `height: 150` with zero calculation** *still* didn't shrink the `ScrollView`. Swapping the `ScrollView` for a plain `<View>` at the exact same spot, same hardcoded height, worked immediately and correctly. Conclusion, confirmed by that swap: **`<ScrollView>` itself silently ignores an explicit `height` in its own `style` in this nested context on iOS** — not a flex-reset issue, not a math issue, a `ScrollView`-specific quirk.

**Actual fix, in all three chat screens:** the `ScrollView` now *always* stays `{ flex: 1 }` (the shape already proven safe) and is wrapped in a plain `<View>` that receives the explicit computed height instead (`keyboardOffset > 0 && chatAreaHeight > 0 ? { height: chatAreaHeight - keyboardOffset - 64, marginBottom: 12 } : { flex: 1, marginBottom: 12 }`) — i.e. `<View style={heightOrFlex}><ScrollView style={{flex:1}}>...</ScrollView></View>`. The `View` respects an explicit height reliably; the `ScrollView` never needs one. **General lesson for this codebase: never put a conditional/computed explicit `height` directly on a `<ScrollView>`'s own `style` — wrap it in a plain `View` that owns the height instead, and give the `ScrollView` `flex: 1` unconditionally.** This was reached by isolating one variable at a time (values → math → flex reset → hardcoded value → component swap) with a visible debug readout at each step, not by guessing at a plausible-sounding cause — worth repeating that process before touching this again if it ever regresses.

## Robustness Pitfalls (learned the hard way this session — watch for these patterns)

1. **Never gate `setLoading(false)` behind a `try` with no `catch`.** `CoachPrograms.tsx` and `CoachTrainees.tsx` both originally had a load effect where any Supabase error (flaky network, RLS hiccup) left the screen stuck on a full-screen spinner forever — including hiding action buttons like "Add Program" that had nothing to do with the failing query. Fix pattern: always `try { ... } catch { setLoadError(true) } finally { setLoading(false) }`, and don't gate primary actions behind a data-load spinner if they don't actually depend on that data.
2. **Hooks must never sit after an early `return`.** `WorkoutScreen.tsx` had a `useMemo` positioned after two conditional early returns (`if (loadingWorkout) return...`, `if (isPending) return...`), so the hook only ran once loading finished — a different hook count between the first and second render, which crashes with "Rendered more hooks than during the previous render." Always put every hook call before any conditional return, no exceptions.
3. **Every `<Modal>` needs `onRequestClose`.** None of the ~18 `Modal`s in the app passed it — on Android, the hardware/gesture back button does nothing while a `Modal` is open unless `onRequestClose` is wired up, which reads as "stuck" (reported first via the coach↔trainee chat modal, but it was universal). Fix pattern: `onRequestClose` should call the exact same handler as the modal's own visible close/X button, so both paths behave identically.
4. **A `flex: 1` child needs a bounded ancestor, not just any ancestor.** `CoachTrainees.tsx`'s trainee-detail modal was a bottom sheet (`maxHeight: '90%'`, no `flex`) containing a `ScrollView` styled `flex: 1` — since the sheet itself only sizes to its content (bounded by `maxHeight`, not stretched to fill), the `ScrollView` had no resolved height to flex into and collapsed to ~0, so the tab content was there in the tree but invisible on screen. Reported as "menu comes up but you can't see the information." Fixed by making the modal genuinely full-screen (`SafeAreaView` + `flex: 1` sheet) instead of patching around it — a `flex: 1` descendant only works if every ancestor up the chain is itself flexed/bounded, not auto-sized.
5. **`KeyboardAvoidingView`'s `behavior` prop needs a real value on Android too — `undefined` disables it entirely.** `FoodLogScreen.tsx`'s inline meal-substitute `TextInput` (see Nutrition Plans & Food Log below) was covered by the keyboard on Android because its wrapper used `behavior={Platform.OS === 'ios' ? 'padding' : undefined}` — every other `KeyboardAvoidingView` in the app correctly uses `'height'` on Android, not `undefined`; this one didn't, and Android is the tested platform (see Dev Environment Setup). Fixed, but did not fully resolve the underlying "can't see what I'm typing" report on its own — see next point.
6. **Don't try to scroll a `TextInput` into view above the keyboard inside a plain `ScrollView` on Android by hand — there's no first-party solution, and two different measure-and-`scrollTo` attempts (`onFocus` + `measureLayout` against a `findNodeHandle`'d ancestor; then `Keyboard.addListener('keyboardDidShow', ...)` + `measureInWindow` against the keyboard's reported height) both failed on-device for `FoodLogScreen.tsx`'s meal-substitute note field.** Stopped hand-rolling it and moved the note entry into a small `Modal` instead (`overlay`/`sheet`/`KeyboardAvoidingView` pattern, shared with the trainee's coach-chat modals elsewhere in the app) — a modal sits above the keyboard by construction, no position math needed. **General lesson: when an inline `TextInput` inside a scrollable list needs to stay visible above the keyboard on Android, default to a modal/bottom-sheet for that input rather than computing a scroll offset** — it reuses an already-proven pattern instead of a fragile one.
7. **Never have two separate `<Modal>` components both `visible={true}` at once — iOS won't reliably show/register touches on the second one stacked over the first (Android tolerates it fine).** This bit twice in the same session, both in the coach-facing "manage X" screens where a detail/editor modal has buttons that open a further picker modal on top of it:
   - `CoachTrainees.tsx`: "Assign Plan" and "Build Calorie & Macro Plan", inside the already-open trainee-detail modal, opened a *second* modal (the nutrition-template picker / `CalorieCalculatorModal`) without closing the first. Fixed via a `nutritionTrainee` capture state: close the trainee-detail modal (`setSelectedTrainee(null)`) before opening either nutrition modal, restore it on that modal's close/cancel/success.
   - `CoachPrograms.tsx`: the Add/Edit Program modal's "Manage Library" link (opens `ExerciseLibraryManager`) and its per-exercise "Select exercise name" field (opens the exercise name-picker modal) had the identical bug — both open a second modal without closing Add/Edit Program first. Fixed with the same capture-and-restore shape, generalized slightly since two different outer modals (`showAddProgram`/`showEditProgram`) share the same two inner modals: a single `reopenAfterModal: 'add' | 'edit' | null` state plus `closeOuterForInner(which)` / `reopenOuterAfterInner()` helpers, wired into every place either inner modal opens or closes (including `openNamePicker`, `handlePickName`, `handleAddNewName`, and both the picker's `onRequestClose` and its own X button).
   - **Correction, found later: `openAssignModal`/`openEditModal` ("Assign New Workout" / workout "Edit", `CoachTrainees.tsx`) had this exact same bug too** — an earlier version of this note claimed the workout side already had the correct pattern, but the code never actually called `setSelectedTrainee(null)` before opening; `openAssignModal`'s own comment *described* the capture-and-restore shape while the function itself didn't do the "close the outer modal first" half of it. Reported as "press Edit, nothing happens until I exit the trainee page" — exactly the documented symptom, just not connected back to this note at the time. Fixed the same way as the other two bullets above: `setSelectedTrainee(null)` added to both `openEditModal`/`openAssignModal`, with `closeEditModal`/`closeAssignModal` restoring it on every close path (X, `onRequestClose`, Cancel, and the save-success path). **Lesson on top of the lesson: a comment asserting a pattern is followed is not proof the code follows it — when auditing for this bug, check what `setSelectedTrainee(null)` actually gets called, not what the nearby comment says.**
   - **Rule of thumb: before opening any new `<Modal>` from inside code that's already rendering inside another visible `<Modal>`, close the outer one first** (capturing whatever state it was holding, if the new modal or its callbacks need it), and restore it when the inner one closes. None of the outer modal's in-progress form state needs to live on its visibility flag for this to be safe — check that it doesn't (it shouldn't, per the general React state-design in this codebase) before assuming a close/reopen won't lose data.
8. **A decrement-per-tick countdown "freezes" when the app is backgrounded — RN fully suspends JS timers, it doesn't just slow them down.** `WorkoutScreen.tsx`'s rest timer used to store `secondsLeft` and decrement it via a `setTimeout` re-armed every second; while backgrounded, no ticks fire at all, so it'd sit frozen at whatever value it hit right before backgrounding and then resume counting down from there once foregrounded — silently understating how much rest time had actually passed. **Fix pattern: for any UI countdown/timer that must reflect real elapsed time across a possible backgrounding, store a fixed target timestamp (`endAt = Date.now() + durationMs`) instead of a decrementing counter, and derive the displayed remaining time from `endAt - Date.now()` on every tick** — this is correct by construction the moment the app resumes, with no special-case backgrounding logic needed. Pair it with an `AppState.addEventListener('change', ...)` → `'active'` handler that forces one extra recompute immediately on foreground, so the display doesn't wait up to a full tick interval to visibly correct itself.
9. **A native module call can throw synchronously and crash the whole app uncaught — backgrounding-adjacent audio calls especially.** Fixing pitfall #8 above introduced a new crash: the rest timer's tick sound (`tickPlayer.play()`, `expo-audio`) fired from the `AppState` 'active' recompute or an interval tick landing right at a background transition, and iOS refuses to activate an `AVAudioSession` while backgrounded/mid-transition — `UnexpectedException: Session activation failed (ExpoModulesCore/SyncFunctionDefinition.swift)`, an uncaught JS error that crashed the app (repro: background the app while resting, foreground briefly, then background again right before the timer hits its final 5 seconds). Fixed by (a) only attempting playback when `AppState.currentState === 'active'`, and (b) wrapping the call in `try/catch` anyway, since the check itself has a race window (backgrounding can start in the instant between the check and the native call). **General lesson: any call into a native module that can plausibly be foreground-only (audio, camera, sensors) needs a `try/catch` around it regardless of any `AppState` guard — Expo's sync native bridge throws synchronously, it doesn't reject a promise, so a bare call can crash the whole app instead of just failing that one feature.**
10. **`expo-notifications` crashes the whole app the instant it's *imported* on Android inside Expo Go — not just when you call a push/remote-token function.** Repro: `[runtime not ready]: Error: expo-notifications: Android Push notifications (remote notifications) functionality provided by expo-notifications was removed from Expo Go with the release of SDK 53. Use a development build instead of Expo Go.` — thrown from the module's own top-level setup code (`addPushTokenListener`, called automatically on import), even though `restNotifications.ts` (see "Rest timer between sets" above) only ever uses *local* scheduled notifications, nothing push/remote at all. Expo Go's check doesn't distinguish local from remote usage — merely having the module loaded is enough. **A `Platform.OS === 'android'` runtime guard placed after a static top-level `import * as Notifications from 'expo-notifications'` does NOT help** — the static import is hoisted and always evaluates regardless of any code that runs after it. Fixed in `restNotifications.ts` by switching to `import type * as NotificationsType from 'expo-notifications'` (type-only — erased at compile time, no runtime `require()`) for typing, plus a `getNotifications()` helper that lazily `require('expo-notifications')`s the real module only when NOT `Platform.OS === 'android' && Constants.executionEnvironment === ExecutionEnvironment.StoreClient` (Expo Go, detected via the newly-added `expo-constants` dependency) — every exported function checks this and no-ops (returns `null`/does nothing) rather than crashing when it's unavailable. iOS Expo Go is unaffected (Apple didn't remove local-notification support there) — this is Android + Expo Go specifically; a dev-client/EAS build on Android would also be unaffected (only Expo Go itself carries the SDK 53 restriction). **General lesson: for any Expo module known to have Expo Go restrictions, prefer a lazy `require()` behind an environment check over a static `import` + runtime guard — some modules have crash-on-import side effects that a downstream `if` can't prevent.**

### Editing an assigned plan's calories auto-scales its macros (and its meals, if any)
Per feedback ("if the coach chooses to change the cals to 2400, the macros should change as well according to the percentages before"): the DAILY TARGETS "CALORIES" field's `onChangeText` is `handlePlanCaloriesChange` (`CoachTrainees.tsx`), not a plain `setPlanCalories`. **Scaling every macro's grams by the same factor the calorie total changed by is mathematically equivalent to preserving each macro's own % of calories** (if protein was 30% of calories before, it's still 30% after) — so this works from whatever protein/carbs/fat values were already in the editor, without needing `plan.calc_inputs.macro_split` (`null` for template-assigned or manually-typed plans, only calculator-built ones have it).
- **Scales from a frozen `planEditBaseline` ref snapshot, not the previous keystroke's value — this distinction matters and was a real bug in the first version of this feature.** Computing `scale` against the value from the immediately-prior keystroke compounds rounding error across a multi-digit edit: clearing "2500" character-by-character before typing "2000" passes through several tiny intermediate "calorie" values (e.g. `250`, `25`, `2`), each shrinking the macros further, and a macro that rounds down to `0` along the way gets **permanently stuck at 0** for the rest of that edit (a `> 0` guard meant to skip already-blank fields also skips a field that only *became* 0 from compounding). `captureCaloriesEditBaseline` freezes a `{calories, protein, carbs, fat, meals}` snapshot on the Calories field's `onFocus` (re-freezing on every re-focus, so a manual edit to Protein/Carbs/Fat or a meal swap made in between correctly becomes the new "before" reference); `handlePlanCaloriesChange` always computes `scale = newCals / baseline.calories` against that fixed snapshot on every keystroke, so the *path* typed no longer matters — only the final committed value does. `openEditPlanEditor` also seeds the ref as a defensive fallback, in case a change is ever received before the field's first focus.
- **If the plan has a calculator-built `meals` array, every meal is rescaled by the same factor in the same keystroke** — each meal's `target_*`/`actual_*` calorie and macro fields, plus its `items`' gram/ml quantities (via `mealLibrary.ts`'s `scaleItem`, exported for this reuse) — so the per-meal breakdown shown in the "MEALS" section above stays consistent with the new daily totals. `handleSelectMealFromPicker` (the "Change" meal-swap flow) also updates `planEditBaseline.current.meals` after a successful swap, so a *subsequent* calorie edit scales from the meal the coach just picked, not a stale one from when the editor first opened.

The Nutrition tab's Edit isn't a second stacked `<Modal>` — `editingPlanId` is inline state rendered inside the *same* still-open Trainee Detail modal — so it needed a different fix for the "same" symptom the coach reported. The Program/Nutrition/Weight/Steps tab body (everything except Chat) is wrapped in its own `KeyboardAvoidingView` with `behavior={Platform.OS === 'ios' ? 'padding' : 'height'}`, added when the inline plan editor's Notes/Water fields needed keyboard clearance. Per this app's own three-times-confirmed "Chat keyboard-avoidance" lesson above, **`'padding'`/`'height'` behavior has never held up reliably inside a `<Modal>` in this codebase, on either platform** — and this wrapper reproduced the same "content inside doesn't reliably take visible effect" shape of symptom for a *plain button press* (no keyboard even involved), consistent with 'padding' occasionally computing/retaining a stale nonzero padding value from an earlier keyboard interaction elsewhere in the same still-mounted modal instance, pushing the freshly-rendered content out of the visible viewport until the whole modal (and thus the KeyboardAvoidingView) was torn down and remounted fresh. Fixed the same way the Chat tab was: `behavior={Platform.OS === 'ios' ? undefined : 'height'}` — **Android's value is untouched, unconditionally, per standing instruction not to touch the Android keyboard behavior that's already working** — plus a `contentContainerStyle={{ paddingBottom: keyboardOffset }}` on the ScrollView (same `useKeyboardOffset()` already used for Chat) so a field near the bottom (Notes, Water) can still be scrolled up past the keyboard by hand on iOS now that nothing does it automatically.

## Performance & Efficiency Patterns

### General Rules Applied
- Use `Promise.all([...])` for independent DB calls that can run in parallel — never sequential `.then()` chains for unrelated queries.
- Wrap expensive computed values in `useMemo` — only recalculate when specific dependencies change.
- Wrap event handlers and callbacks in `useCallback` when passed as props to child components.
- Wrap list-item components in `React.memo` when rendered in large maps (leaderboards, medal grids).
- Update local state directly after mutations instead of refetching from DB when possible.

### Fixes Applied Per File

**`db.ts`**
- `getExerciseWeightLogs` has a default `limit: 100` — prevents unbounded fetches.
- `getAllUserFriendships(userId)` — single query for all friendship records; avoids N per-user `getFriendshipStatus` calls during search.
- `getUnreadMessagesForCoach` does 2 queries (messages, then a single `in()` lookup for sender profiles) rather than an embedded join, to avoid depending on guessed FK constraint names.

- **Security — the gamification-integrity gap above is now fixed: XP/level/streak/medal awards moved fully server-side.** `scripts/secure_gamification.sql` is a substantial migration — read its own header comment for the full picture before touching any of this again. Summary:
  - **New RPCs, all SECURITY DEFINER, all operating only on `auth.uid()` (never a client-supplied id, except `claim_coach_connected_medal`/`accept_friend_request` which independently re-verify the caller's relationship to whichever other user they affect — see below):** `complete_workout_session(...)` (replaces `saveWorkoutSession` + `recalculateStreak` + `evaluateAndAwardMedals` + the xp/level `updateProfile` call, atomically — the trainee's one and only workout-completion path now), `evaluate_and_award_medals()` (standalone entry point, used after saving the biometric profile for New Adventure/Profile Complete), `recalculate_streak()` (standalone, used after nutrition tracking), `claim_coach_connected_medal(p_trainee_id)` (replaces the old `awardMedalIfNew` call in `acceptCoachRequest`), `accept_friend_request(p_requester_id)` (replaces the direct `friendships` update + cross-user XP write in `acceptFriendRequest`).
  - **Internal-only helpers** (`_compute_streak`, `_evaluate_and_award_medals` — leading underscore, no grant to any role) hold the actual ported logic, reused by the public wrappers above. **PostgreSQL grants EXECUTE to `PUBLIC` by default on every newly-created function** — an easy, real mistake to make here specifically: an early version of this migration correctly revoked-and-regranted every *public-facing* RPC but missed the `revoke all ... from public` on `_evaluate_and_award_medals` itself, which (being SECURITY DEFINER) would have let anyone call it directly with an arbitrary `p_trainee_id` to award medals/XP to *any* account. Caught in review before this ever shipped — **any new internal helper function added to this file needs an explicit `revoke all on function ... from public` of its own; never assume "I didn't grant it" means "no one can call it."**
  - **`db.ts`:** `evaluateAndAwardMedals()` and `recalculateStreak()` are now thin RPC wrappers (no params — everything server-derived); `completeWorkoutSession(...)` replaces the old direct `saveWorkoutSession` export; `awardMedal`/`awardMedalIfNew`/`getWorkoutSessionCount`/`getDistinctActiveDayCount`/`hasCompletedInHourRange`/`getMaxDailySteps`/the client-side `computeStreakFromActiveDays`/`getStreakActiveDays` are all deleted (dead once their only callers moved server-side, not left as orphaned unreachable code). `acceptFriendRequest`'s signature dropped its now-unused `userId` param.
